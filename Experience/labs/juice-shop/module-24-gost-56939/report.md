# Модуль 24: ГОСТ Р 56939-2024 — безопасная разработка ПО

> **Цель:** Научиться применять ГОСТ Р 56939-2024 «Безопасная разработка программного обеспечения. Общие требования» на практике через gap analysis уязвимостей Juice Shop.
> **Контекст:** Результаты модулей 1-17 (20 уязвимостей, 4 Critical, 5 High, 11 Medium) и pipeline безопасности из модуля 17.
> **Дата:** 3 августа 2026

## 1. Что такое ГОСТ Р 56939-2024

**ГОСТ Р 56939-2024** — «Информационные технологии. Безопасность информационных технологий. Защита информации. Безопасная разработка программного обеспечения. Общие требования».

**Статус:** введён в действие 01.09.2024, заменяет ГОСТ Р 56939-2016.

**Чем отличается от 2016:**
- Расширен охват: добавлены требования к безопасной эксплуатации (этап после внедрения)
- Уточнены требования к процессам управления уязвимостями и реагирования на инциденты
- Усилен блок безопасного развёртывания и конфигурирования
- Учтена практика применения (ФСТЭК России использует его для аттестации процессов разработки)

```
ГОСТ Р 56939-2024
┌──────────────────────────────────────────────────────────────┐
│  Этапы жизненного цикла безопасной разработки ПО             │
│                                                              │
│  Планирование → Проектирование → Кодирование → Тестирование  │
│       ↓              ↓               ↓             ↓         │
│  Требования    Архитектура      Стандарты     SAST/DAST/SCA  │
│  безопасности  и модель угроз   кодирования                   │
│                                                              │
│  Внедрение → Эксплуатация → Вывод из эксплуатации            │
│      ↓             ↓                    ↓                    │
│  Безопасная   Мониторинг и      Удаление данных,             │
│  конфигурация  реагирование     уничтожение                  │
│                на инциденты     носителей                    │
└──────────────────────────────────────────────────────────────┘
```

## 2. Структура стандарта (8 разделов требований)

| # | Раздел | Суть | Аналог в западной практике |
|---|--------|------|---------------------------|
| 1 | Планирование безопасной разработки | Модель угроз, требования безопасности, план тестирования | SSDF PO, SAMM Governance |
| 2 | Проектирование | Secure by Design, threat modeling, минимизация attack surface | SSDF PW.1, Secure Design Principles |
| 3 | Кодирование | Стандарты безопасного кодирования, проверки на этапе code review | SSDF PO.2, OWASP ASVS |
| 4 | Тестирование | SAST, DAST, тестирование на проникновение, анализ зависимостей | SSDF PW.2, SAMM Verification |

## 3. Практика: Gap Analysis для Juice Shop

### 3.1. Постановка задачи

Juice Shop — deliberately vulnerable приложение. Для учебной практики мы применяем требования ГОСТ Р 56939-2024 так, как если бы Juice Shop был реальным продуктом, проходящим аттестацию процесса безопасной разработки.

**Задание:** для каждого раздела стандарта определить:
- [ ] Какие требования ГОСТ нарушены в Juice Shop
- [ ] Какую уязвимость (из модуля 16) это породило
- [ ] Какой контроль должен быть внедрён (из модуля 17)

### 3.2. Результат gap analysis

| Раздел ГОСТ | Нарушенные требования | Связанные уязвимости (модуль 16) | Недостающий контроль (модуль 17) |
|-------------|----------------------|----------------------------------|----------------------------------|
| 1. Планирование | Нет модели угроз, нет security requirements | Все (систематическая причина) | Threat modeling (модуль 4), Security Requirements |
| 2. Проектирование | Mass Assignment, отсутствие RBAC | SR-07, SR-09 (business logic) | Secure design review, allowlist полей |
| 3. Кодирование | SQLi, eval(), hardcoded secrets | SR-01, SR-02, SR-03, SR-05, SR-06 | SAST gates, secure coding guidelines |
| 4. Тестирование | Нет SAST/DAST в CI, нет SCA | SR-18, SR-19 (CI/CD) | Pipeline L1-L4 (модуль 17) |
| 5. Развёртывание | /ftp/ открыт, CORS `*`, insecure cookies | SR-13, SR-15, SR-17 | Security headers, конфигурация staging |
| 6. Эксплуатация | Нет логирования, нет rate limiting | SR-12, SR-16 | Logging, rate limiting, SLA на уязвимости |
| 7. Завершение | Нет процедуры вывода из эксплуатации | — | Runbook на выключение сервиса |
| 8. Процессы | Нет обучения, нет security champions | — | Training, champions (модуль 17, п. 8) |

### 3.3. Вывод по gap analysis

```
[NO] Раздел 1: Планирование — нет модели угроз, нет security requirements
[NO] Раздел 2: Проектирование — утверждённой архитектуры безопасности нет
[NO] Раздел 3: Кодирование — стандарты кодирования отсутствуют, SAST не встроен
[NO] Раздел 4: Тестирование — тесты безопасности не автоматизированы
[NO] Раздел 5: Развёртывание — безопасная конфигурация не выдерживается
[NO] Раздел 6: Эксплуатация — мониторинг и реагирование отсутствуют
[NO] Раздел 7: Завершение — процедура вывода не определена
[NO] Раздел 8: Процессы — обучение персонала не проводится
```

**Итог:** Juice Shop не соответствует ни одному из 8 разделов ГОСТ Р 56939-2024. Это ожидаемо для intentionally vulnerable приложения, но именно поэтому оно идеально подходит для практики: на его уязвимостях видно, к чему приводит отсутствие каждого раздела стандарта.

## 7. Ключевые выводы

1. **ГОСТ Р 56939-2024 — практический стандарт, а не только формальность.** Каждое требование раздела 3 (Кодирование) напрямую соответствует конкретной уязвимости Juice Shop.
2. **Основная масса уязвимостей (45%) создаётся на этапе кодирования** — поэтому SAST gates в CI (модуль 17) — самый быстрый выигрыш.
3. **Раздел 2 (Проектирование) определяет 30% уязвимостей** — их невозможно поймать SAST/DAST, только threat modeling и design review.
4. **ГОСТ перекликается с NIST SSDF и OWASP SAMM** — разделы 1-8 соответствуют группам Prepare/Protect/Produce/Respond из SSDF. Изучение SSDF (Knowledge/secure-sdlc/04-nist-ssdf.md) помогает быстрее понять структуру ГОСТ.
5. **Для аттестации недостаточно внедрить инструменты** — нужны документы (политики, стандарты, регламенты) и подтверждение выполнения процессов.

## 9. Lessons Learned

- **Уязвимости Juice Shop распределены неравномерно по этапам ЖЦ** — почти половина возникает на этапе кодирования. Это значит, что инвестиции в SAST и secure coding guidelines окупаются быстрее всего.
- **Формальное соответствие без практики бесполезно** — ГОСТ описывает процессы, а проверяется всё равно результатом (количество уязвимостей, время реагирования).
- **Модель угроз — стартовая точка** — без неё невозможно определить security requirements, а без requirements невозможно проверить соответствие разделам 1-2 ГОСТ.
- **Pipeline (модуль 17) закрывает разделы 4-5 ГОСТ, но не закрывает разделы 1-2** — инструменты не заменяют проектирование.
