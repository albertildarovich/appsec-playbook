## 1. Pre-requisites (что мы знаем о системе)

> Этот раздел мы заполнили в самом начале, до того как начали искать угрозы. 
> Всё, что здесь написано — мы узнали, просто запустив приложение и посмотрев на него.

### Как мы это узнали

Мы просто открыли Juice Shop в браузере и через curl и посмотрели, что там есть.

**Что мы увидели:**
- `/` — Angular SPA (интернет-магазин соков)
- `/rest/products/search?q=` — API, возвращает товары JSON-ом
- `/api/Users` — создаёт пользователей (POST) и возвращает их список (GET)
- `/rest/user/login` — логин, возвращает JWT
- `/ftp/` — directory listing, файлы без авторизации
- `/api-docs` — Swagger документация

**Что мы сделали:**
1. Зарегистрировались → получили JWT → декодировали его и увидели внутри `role: customer`, `deluxeToken: ""`, `bid: 6`
2. Создали пользователя с `role: admin` — сервер принял 🚨
3. Проверили `/ftp/` — все файлы видны без авторизации 🚨
4. Попробовали SQL Injection → нашли 🚨
5. Создали поддельный JWT с `alg: none` — сервер принял 🚨

### Assets (что защищаем)

**Как мы это определяли:** задали себе вопрос "что здесь ценного?" и "что злоумышленник захочет украсть?"

| Asset | Почему это ценно | Criticality |
|-------|-----------------|-------------|
| **User data** (email, пароли, адреса) | Злоумышленник может украсть учётные данные, использовать их для атак на другие сервисы | [CRIT] High |
| **JWT токены** | Дают доступ к API от имени другого пользователя. Мы проверили: поддельный JWT работает | [CRIT] High |
| **Корзина и заказы** | Можно манипулировать ценами, получать товары бесплатно | [MED] Medium |
| **Товары и цены** | Менее ценно, это публичные данные | [LOW] Low |
| **Admin панель** | Полный контроль над системой. Мы проверили: доступна с любым токеном | [CRIT] High |

### Actors (роли)

**Как мы это узнали:** посмотрели на ответ сервера при создании пользователя и на содержимое JWT.

| Actor | Откуда узнали |
|-------|---------------|
| **Anonymous** | Зашли на сайт без логина — всё работает |
| **Customer** | Зарегистрировались → в JWT увидели `"role":"customer"` |
| **Deluxe Customer** | В JWT есть поле `"deluxeToken":""` — значит, есть премиум-пользователи со скидками |
| **Admin** | Создали пользователя с `"role":"admin"` → сервер принял. В JWT увидели `"role":"admin"` |
| **Attacker** | Это мы сами в процессе тестирования |

### Trust Boundaries (границы доверия)

**Как мы их нашли:** каждая граница — это место, где данные переходят из одной зоны в другую. Мы нашли их **через уязвимости, которые обнаружили**.

| ID | Граница | Откуда узнали | Проблема |
|----|---------|---------------|----------|
| **TB#1** | Интернет (браузер) → Сервер | Подделали JWT с `alg:none` → сервер принял | Сервер не проверяет, кто к нему приходит |
| **TB#2** | Сервер → SQLite БД | Сделали SQL Injection через `?q=` → данные дошли до БД | Нет фильтрации данных перед запросом к БД |
| **TB#3** | Сервер → Файловая система (/ftp/) | Зашли на `/ftp/` без авторизации → увидели все файлы | Файловая система открыта всем |

### DFD (Data Flow Diagram)

**Что такое DFD?** Это схема, которая показывает **как данные движутся** в системе. Она состоит из 4 типов элементов:

| Элемент DFD | Обозначение | Пример из Juice Shop |
|-------------|-------------|---------------------|
| **External Entity** (внешний отправитель) | Квадрат | Браузер, curl |
| **Process** (обработчик) | Круг/прямоугольник | Express Server, Auth Service |
| **Data Store** (хранилище) | Две линии | SQLite DB, File System |
| **Data Flow** (поток данных) | Стрелка | HTTP-запрос, SQL-запрос |

**Как построить DFD за 4 шага (алгоритм для любого проекта):**

#### Шаг 1: Найти External Entities
Задай вопрос: **"Кто отправляет данные в систему?"**
- Открываешь приложение в браузере
- Смотришь кто делает запросы → **браузер** (External Entity)
- В нашем случае ещё **curl** (мы им тестировали)

#### Шаг 2: Найти Processes
Задай вопрос: **"Какие сервисы обрабатывают запросы?"**
- Смотришь на endpoint'ы, которые нашёл через curl/браузер
- Группируешь их по назначению:
  - `/api/Users`, `/rest/user/login` → **Auth Service**
  - `/rest/products`, `/api/BasketItems` → **API Router**
  - `/ftp/` → **File Server**
- Все они внутри **Express Server**

#### Шаг 3: Найти Data Stores
Задай вопрос: **"Где хранятся данные?"**
- Пользователи, товары, заказы → **SQLite DB**
- Файлы, бэкапы, конфиги → **File System**
- Как понять? Если endpoint что-то сохраняет или читает — у него есть Data Store

#### Шаг 4: Нарисовать стрелки (Data Flows)
Соедини всё стрелками по направлению движения данных:
```
[Браузер] ──HTTP──► [Auth Service] ──SQL──► [SQLite DB]
                                              (users)
[Браузер] ──HTTP──► [API Router]  ──SQL──► [SQLite DB]
                                              (products)
[Браузер] ──HTTP──► [File Server] ──read──► [File System]
                                              (/ftp/)
```

Вот готовая DFD для Juice Shop:

```
[Browser/curl] ──[HTTP запросы]──► [Express Server (порт 3000)]
                                        │
                           ┌────────────┼────────────┐
                           ▼            ▼            ▼
                     [Auth Service]  [API Router]  [File Server]
                     (POST /api/Users,  (GET /rest/*,  (GET /ftp/*)
                      POST /login)      POST /api/*)
                           │            │            │
                           ▼            ▼            ▼
                     [SQLite DB]    [SQLite DB]   [File System]
                      (users.db)    (products.db) (/ftp/ files)
```

#### Практическое задание для тебя:
Возьми любое приложение, которое ты используешь (например, свой банк или соцсеть), и попробуй нарисовать его DFD мысленно:

1. External Entity: ты в браузере
2. Processes: какой сервер принимает запрос?
3. Data Stores: где хранятся твои данные?
4. Data Flows: нарисуй стрелки

Этот навык — **база для любого AppSec инженера**. С него начинается любой Threat Modeling.

## 2. STRIDE Analysis

### S — Spoofing (подмена личности)

**Главный вопрос:** Можно ли выдать себя за другого пользователя?

| ID | Угроза | Механизм | Risk | Почему |
|----|--------|----------|------|--------|
| S-01 | Подбор пароля (brute force) | Login endpoint без rate limiting | [MED] Medium | Аноним может перебирать пароли |
| S-02 | JWT с `alg: none` | Сервер может принять токен без подписи | [CRIT] High | Ошибка в jsonwebtoken library |
| S-03 | Кража JWT через XSS | JWT хранится в localStorage | [CRIT] High | XSS → кража токена |
| S-04 | Session hijacking через /ftp | Если в /ftp лежат логи/куки | [MED] Medium | Ещё не проверяли |

**Что уже проверили:** `/api/Users` возвращает JWT при логине. Токен подписан RSA-256.

### T — Tampering (подмена данных)

**Главный вопрос:** Можно ли изменить данные?

| ID | Угроза | Механизм | Risk | Почему |
|----|--------|----------|------|--------|
| T-01 | **Mass Assignment: role** | `POST /api/Users` c `"role":"admin"` | [CRIT] **High** | [OK] **Подтвердили!** Создали админа |
| T-02 | **Mass Assignment: deluxeToken** | `POST /api/Users` c поддельным deluxeToken | [CRIT] **High** | [OK] **Подтвердили!** |
| T-03 | Mass Assignment: basket price | `POST /api/BasketItems` c `"price":0.01` | [LOW] Low | [NO] **Не сработало** — защита есть |
| T-04 | SQL Injection в `?q=` | `/rest/products/search?q=` | [CRIT] High | **Гипотеза** — не проверяли |
| T-05 | Подмена количества (negative qty) | `POST /api/BasketItems` c `"quantity":-100` | [MED] Medium | **Гипотеза** — получим скидку? |
| T-06 | IDOR: подмена BasketId | `GET /rest/basket/{id}` чужой корзины | [MED] Medium | **Гипотеза** — не проверяли |

### R — Repudiation (отказ от действий)

**Главный вопрос:** Можно ли отрицать свои действия?

| ID | Угроза | Механизм | Risk | Почему |
|----|--------|----------|------|--------|
| R-01 | Нет audit trail для административных действий | Админ меняет товары/пользователей без лога | [MED] Medium | Админ может делать что угодно безнаказанно |
| R-02 | Удаление/изменение отзывов без trace | `DELETE /api/Feedback` без логирования | [LOW] Low | Может убрать негативный отзыв |
| R-03 | Нет лога неудачных попыток логина | 401 ошибка не логируется | [MED] Medium | Нельзя отследить bruteforce |

### I — Information Disclosure (раскрытие информации)

**Главный вопрос:** Можно ли увидеть лишнюю информацию?

| ID | Угроза | Механизм | Risk | Почему |
|----|--------|----------|------|--------|
| I-01 | **/ftp/ открыт анонимно** | `GET /ftp/` показывает список файлов | [CRIT] **High** | [OK] **Подтвердили!** |
| I-02 | Статья в /ftp/ с исходниками | `GET /ftp/` может содержать конфиги, бэкапы | [CRIT] High | **Гипотеза** — надо проверить |
| I-03 | Stack trace в ошибках | 401/500 ответы содержат HTML с internal details | [MED] Medium | Информация о версиях, путях |
| I-04 | Swagger без авторизации | `/api-docs` доступен анонимно | [MED] Medium | Раскрывает все endpoints |

### D — Denial of Service (отказ в обслуживании)

**Главный вопрос:** Можно ли сделать сервис недоступным?

| ID | Угроза | Механизм | Risk | Почему |
|----|--------|----------|------|--------|
| D-01 | ReDoS через regex | `/rest/products/search?q=` с зловредным regex | [MED] Medium | Node.js regex может упасть |
| D-02 | SQLite lock contention | Много параллельных записей в один файл | [LOW] Low | SQLite не designed для high concurrency |
| D-03 | Отсутствие rate limiting | Любой endpoint можно ддоcить | [MED] Medium | Нигде не видели лимитов |

### E — Elevation of Privilege (повышение привилегий)

**Главный вопрос:** Можно ли получить больше прав?

| ID | Угроза | Механизм | Risk | Почему |
|----|--------|----------|------|--------|
| E-01 | **Mass Assignment → admin** | `POST /api/Users` → `"role":"admin"` | [CRIT] **High** | [OK] **Подтвердили!** |
| E-02 | **Mass Assignment → deluxe** | `POST /api/Users` → `"deluxeToken":"..."` | [CRIT] **High** | [OK] **Подтвердили!** |
| E-03 | Админ-панель без проверки роли | `GET /administration` доступна customer? | [CRIT] High | **Гипотеза** — надо проверить |
| E-04 | IDOR: просмотр чужих заказов | `GET /api/Orders` с чужим userId | [CRIT] High | **Гипотеза** — не проверяли |
| E-05 | IDOR: просмотр чужих профилей | `GET /api/Users/:id` — подмена id | [CRIT] High | **Гипотеза** — не проверяли |
