# ADR-001: Выбор Keycloak как Identity Provider

## Контекст
Потребовалось централизованное решение для аутентификации и авторизации в нескольких приложениях.
Требования: SSO, RBAC, интеграция с LDAP, self-service управление пользователями.

## Рассматриваемые варианты

| Вариант | Pros | Cons |
|---------|------|------|
| **Keycloak** | Open source, мощный, LDAP, SAML/OIDC, Self-service | Сложный в настройке, нужно администрировать |
| **Auth0** | Cloud, простой, много интеграций | Дорого, vendor lock-in |
| **AWS Cognito** | Интеграция с AWS | Сложный с non-AWS, дорогой на объёмах |
| **Firebase Auth** | Простой, быстрый старт | Только OIDC, нет SAML, vendor lock-in |

## Решение
**Выбрали Keycloak**.

Почему:
- Open source — нет vendor lock-in
- Поддержка SAML + OIDC
- LDAP интеграция (был legacy LDAP)
- Self-service управление пользователями
- Бесплатно (важно для бюджета)

## Какие угрозы закрываем

| Угроза | Как закрыли |
|--------|-------------|
| Разрозненная аутентификация | Единый Identity Provider |
| Слабые пароли | Политика паролей в Keycloak |
| Отсутствие MFA | Включили TOTP |
| Нет централизованного audit | Логи Keycloak в ELK |

## Какие риски остаются

| Риск | Контрмеры |
|------|-----------|
| Misconfiguration Keycloak | Регулярный review конфигов |
| Zero-day в Keycloak | Своевременные обновления |
| Single point of failure | High-availability настройка |
| Role explosion | Регулярный аудит ролей |

## Последствия

- + Централизованное управление доступом
- + SSO для пользователей
- - Нужен администратор Keycloak
- - Сложная первоначальная настройка
- - Дополнительная инфраструктура
