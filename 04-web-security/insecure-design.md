## 1. Что такое Insecure Design?

**Insecure Design** — это ошибки **проектирования** системы, а не ошибки **реализации**.

Код может быть написан **идеально**, но архитектура или бизнес-логика позволяют злоумышленнику добиться своей цели.

### Самая важная мысль

Нужно перестать задавать вопрос:

> *"Как написать безопасный код?"*

И начать задавать вопрос:

> **"Что может пойти не так?"**

Именно это отличает **Security Architect** от обычного разработчика.

### Примеры Insecure Design

| Проблема | Описание |
|----------|----------|
| Отсутствуют лимиты | Можно переводить любые суммы |
| Нет подтверждения | Операция выполняется без MFA |
| Бесконечные запросы | Можно безлимитно запрашивать SMS |
| Доверие клиенту | Сервер принимает цену от браузера |
| Нет сессионных ограничений | Несколько активных reset-токенов |
| Необратимость | Нет возможности отменить/восстановить |

## 2. Insecure Design vs Secure Coding

| Secure Coding | Insecure Design |
|---------------|-----------------|
| Исправляет ошибки **реализации** | Проблема находится **гораздо раньше** |
| SQL Injection, XSS, XXE, Buffer Overflow | Отсутствие лимитов, доверие клиенту, нет MFA |
| **Код написан неправильно** | **Архитектура небезопасна** |

### Ключевой принцип

> Безопасность должна проектироваться **заранее**. Её невозможно полностью "добавить" после завершения разработки.

## 3. Пример №1 — Банковский перевод

### API

```http
POST /transfer
Content-Type: application/json

{
    "amount": 500000000,
    "toAccount": "1234567890"
}
```

Пользователь может отправить **любую сумму** без:
- MFA;
- лимитов;
- проверки поведения;
- подтверждения операции.

### Что здесь не так?

Код может быть **идеальным**:
- ✅ JWT проверяется
- ✅ SQL Injection отсутствует
- ✅ XSS нет
- ✅ CSRF-токен есть

Но проектировщики **вообще не подумали**:
- что аккаунт могут украсть;
- что пользователь может ошибиться;
- что злоумышленник автоматизирует переводы.

### Возможные защиты

| Защита | Описание |
|--------|----------|
| **Лимиты** | Максимальная сумма перевода в день |
| **MFA** | Подтверждение крупных переводов |
| **Анализ аномалий** | Нехарактерное поведение |
| **Задержка** | Для новых получателей |
| **Ручная проверка** | Для сумм выше порога |
| **Подтверждение** | Email/Push уведомление |

## 4. Пример №2 — Never Trust the Client

### ❌ Плохой API

```json
// Запрос от клиента
{
    "productId": 15,
    "price": 100,
    "paid": true
}
```

Почему это плохо? Клиент может изменить:

```json
{
    "price": 1,
    "paid": true
}
```

Если сервер **доверяет** этим данным, можно бесплатно получать товары.

### ✅ Правильная архитектура

Клиент должен отправлять **только**:

```json
{
    "productId": 15,
    "quantity": 2
}
```

Сервер **самостоятельно**:
- получает цену из базы;
- рассчитывает скидку;
- проверяет оплату через платёжный шлюз;
- определяет статус заказа.

### Главный принцип

> **Never Trust the Client**

Никогда не доверять данным от клиента:
- ❌ цена;
- ❌ роль /权限;
- ❌ сумма;
- ❌ статус оплаты;
- ❌ признаки администратора (`isAdmin: true`);
- ❌ любые критически важные данные.

### Демонстрация на Java (Spring Boot)

```java
// ❌ ПЛОХО: доверяем данным от клиента
@PostMapping("/order")
public Order createOrder(@RequestBody OrderRequest request) {
    // request.getPrice() — клиент прислал цену!
    return orderService.create(request);
}

// ✅ ХОРОШО: сервер сам определяет цену
@PostMapping("/order")
public Order createOrder(@RequestBody OrderRequest request) {
    Product product = productRepository.findById(request.getProductId());
    // Цена только из базы
    BigDecimal price = product.getPrice();
    return orderService.create(request.getUserId(), product, request.getQuantity());
}
```

### Демонстрация на Python (FastAPI)

```python
from pydantic import BaseModel

# ❌ ПЛОХО: клиент указывает цену
class OrderRequest(BaseModel):
    product_id: int
    price: float  # ❌ доверяем клиенту
    quantity: int

# ✅ ХОРОШО: только ID товара
class OrderRequest(BaseModel):
    product_id: int
    quantity: int
    # price не принимаем — сервер получит из базы

@app.post("/order")
async def create_order(request: OrderRequest):
    product = get_product(request.product_id)
    total = product.price * request.quantity  # ✅ цена от сервера
    return create_payment(request, total)
```

## 5. Пример №3 — Password Reset

### Типичная реализация

```
GET /reset?token=ABC123
```

### Что нужно проверять

| Аспект | Правильно | Неправильно |
|--------|-----------|-------------|
| **Время жизни** | 15 минут | Сутки, месяц, "навсегда" |
| **Одноразовость** | После использования — недействителен | Можно использовать повторно |
| **Множественные токены** | Новый токен инвалидирует старый | Оба активны |

### Правильная логика

```
1. Запрос сброса
2. Старый токен → INVALID
3. Новый токен → VALID
4. В системе существует только ОДИН активный токен
```

### После смены пароля

```python
# После успешного сброса пароля:
def reset_password(token: str, new_password: str):
    user = verify_reset_token(token)
    
    # 1. Меняем пароль
    user.set_password(new_password)
    
    # 2. Инвалидируем токен
    invalidate_reset_token(token)
    
    # 3. Завершаем ВСЕ активные сессии
    invalidate_all_sessions(user.id)
    
    # 4. Инвалидируем Refresh Token
    invalidate_refresh_tokens(user.id)
    
    # 5. Требуем повторный вход
    return {"message": "Password changed. Please login again."}
```

### Если злоумышленник украл письмо

Кто владеет токеном — тот может изменить пароль.

Поэтому токен должен быть:
- **случайным** (непредсказуемым);
- **короткоживущим** (15 минут);
- **одноразовым** (после использования — недействителен).

## 6. Пример №4 — Rate Limiting

### Проблема

Есть сервис регистрации. Можно бесконечно нажимать **"Получить код"**.

### Последствия

| Последствие | Описание |
|-------------|----------|
| **SMS bombing** | Пользователю приходят сотни SMS |
| **Email bombing** | Почтовый ящик забивается |
| **DoS пользователя** | Телефон/почта непригодны к использованию |
| **Финансовые потери** | Каждая SMS стоит денег |
| **Перегрузка сервиса** | Увеличение нагрузки на инфраструктуру |

### Возможные защиты

```python
# Пример Backoff стратегии
RATE_LIMITS = {
    1:  {"delay": 0,      "action": "allow"},
    2:  {"delay": 10,     "action": "delay"},      # 10 seconds
    3:  {"delay": 30,     "action": "delay"},      # 30 seconds
    4:  {"delay": 120,    "action": "delay"},      # 2 minutes
    5:  {"delay": 0,      "action": "captcha"},    # CAPTCHA required
    6+: {"delay": 0,      "action": "block"}       # Block for 24h
}
```

| Защита | Описание |
|--------|----------|
| **Rate Limiting** | N запросов в минуту |
| **CAPTCHA** | После N попыток |
| **Cooldown** | Задержка между запросами |
| **Backoff** | Увеличивающаяся задержка |
| **IP лимит** | N запросов с одного IP |
| **Email лимит** | N запросов на один email |
| **Device лимит** | N запросов с одного устройства |

## 7. Пример №5 — Удаление аккаунта

### ❌ Плохая архитектура

```
Нажал кнопку → Аккаунт удалён навсегда
```

### Что может случиться?

- случайное удаление;
- угон аккаунта;
- инсайдер;
- ошибка пользователя.

### ✅ Как проектируют зрелые системы

```
Удалить аккаунт
    ↓
Аккаунт → DISABLED
    ↓
30 дней хранится (можно восстановить)
    ↓
Окончательное удаление
```

### Перед удалением

Желательно запросить:
- повторный пароль;
- MFA;
- подтверждение по почте;
- подтверждение через приложение.

## 8. Human Error

> Очень важная идея. Безопасность должна защищать **не только от злоумышленников**, но и **от ошибок пользователя**.

### Примеры Human Error

| Ошибка | Последствие |
|--------|-------------|
| Случайный перевод | Деньги ушли не туда |
| Лишний ноль | Вместо 1000 → 1000000 |
| Неправильный получатель | Перевод чужому человеку |
| Случайное удаление | Потеря аккаунта/данных |

### Как проектировать с учётом Human Error

```python
# ✅ Подтверждение критических операций
def transfer_money(from_account, to_account, amount):
    if amount > DAILY_LIMIT:
        raise RequiresMFA("Transfer exceeds daily limit")
    
    if is_new_recipient(to_account):
        # Задержка для новых получателей
        schedule_transfer(from_account, to_account, amount, delay=24.hours)
        notify_user(f"Transfer to {to_account} will be processed in 24 hours")
        return
    
    # Стандартный перевод
    execute_transfer(from_account, to_account, amount)
```

## 9. Compensating Controls

> Если ошибку **невозможно предотвратить**, необходимо **уменьшить последствия**.

| Контроль | Пример |
|----------|--------|
| **Отмена операции** | "Отменить перевод" в течение 30 минут |
| **Восстановление аккаунта** | Grace period после удаления |
| **Ручное подтверждение** | Оператор проверяет крупные переводы |
| **Задержка выполнения** | 24 часа для новых получателей |
| **Журнал аудита** | Все операции логируются для расследования |
| **Уведомления** | Push/Email/SMS при критических операциях |

## 10. Abuse Cases

Вместо вопроса **"Что должна делать система?"** нужно спрашивать:

> **"Как системой могут злоупотребить?"**

### Кто может злоупотребить?

| Actor | Пример |
|-------|--------|
| **Злоумышленник** | Целенаправленная атака |
| **Пользователь** | Случайная ошибка, импульсивное действие |
| **Сотрудник** | Инсайдер, доступ к админке |
| **Автоматизированный бот** | Скрипт, краулер, DDoS |
| **Случайность** | Ошибка оператора, сбой системы |

### Пример Abuse Case анализа

**Функция:** Перевод денег

| Abuse Case | Защита |
|------------|--------|
| Злоумышленник угнал аккаунт | MFA для крупных сумм, лимиты |
| Пользователь ошибся суммой | Подтверждение, отмена операции |
| Бот перебирает получателей | Rate limiting, CAPTCHA |
| Инсайдер меняет лимиты | Audit log, разделение ролей |
| Сбой: двойной перевод | Идемпотентность запросов |

## 11. Главные вопросы AppSec-инженера

При анализе новой функции задавай себе:

| Вопрос | Что проверяем |
|--------|---------------|
| **Если аккаунт украдут?** | Что сможет сделать злоумышленник? |
| **Если пользователь ошибётся?** | Можно ли отменить действие? |
| **Если данные изменят?** | Доверяем ли мы клиенту? |
| **Если отправить миллион запросов?** | Есть ли ограничения? |
| **Если украдут ссылку?** | Можно ли использовать её повторно? |
| **Если украдут телефон?** | Достаточно ли одной активной сессии? |
| **Если разработчик забудет?** | Безопасна ли система по умолчанию? |

## 12. Interview Questions

### Базовые вопросы

| Вопрос | Ответ |
|--------|-------|
| **Почему Insecure Design нельзя исправить одним патчем?** | Потому что проблема находится в архитектуре, а не в коде. Исправление требует перепроектирования. |
| **Что важнее: безопасный код или безопасная архитектура?** | Нужно и то, и другое. Идеальный код не спасёт плохую архитектуру. |
| **Что такое Never Trust the Client?** | Сервер не должен доверять данным, пришедшим от клиента (цена, роль, статус оплаты). |
| **Что такое Abuse Cases?** | Анализ того, как системой могут злоупотребить. В отличие от Use Cases, которые описывают "правильное" поведение. |

### Продвинутые вопросы

| Вопрос | Ответ |
|--------|-------|
| **Как искать Insecure Design?** | Не искать уязвимости. Искать: "Что может пойти не так?" |
| **Как проектировать защиту от Human Error?** | Подтверждение, отмена, Grace Period, лимиты, автоматические уведомления. |
| **Что такое Compensating Controls?** | Если риск нельзя устранить — уменьшить последствия. |
| **Как ответить на "это только для DEV"?** | Временные решения становятся постоянными. Нет ничего более постоянного, чем временное. |

### Как отвечать на интервью (формулировка)

> **Insecure Design** — это ошибки проектирования системы, при которых даже корректно реализованный код остаётся небезопасным. Для предотвращения подобных проблем необходимо проводить **Threat Modeling**, анализировать **Abuse Cases**, учитывать **ошибки пользователей** и проектировать **защитные механизмы ещё до начала разработки**.
