# Trade-off: JWT vs Session

## Проблема

Как управлять аутентификацией пользователей: использовать stateless JWT или stateful server-side sessions?

---

## Вариант A: Session-based (stateful)

### Как работает
```
Login → Server создаёт Session → Session ID в HttpOnly Cookie
Каждый запрос → Server ищет Session в Redis/DB
```

### Преимущества
- **Мгновенный отзыв** — удалил session из Redis, пользователь вышел
- **Полный контроль** — сервер управляет lifecycle
- **Никаких секретов на клиенте** — session ID — просто случайная строка
- **Меньше данных** — в куке только ID, все данные на сервере
- **Простой invalidation** — сброс пароля → удалил все сессии

### Недостатки
- **Нужно хранилище** — Redis/DB для сессий (ещё один компонент)
- **Медленнее** — каждый запрос требует lookup
- **Сложнее горизонтальное масштабирование** — нужно sticky session или shared Redis
- **Больше нагрузки** — каждый запрос → запрос в Redis

### Когда выбирать
- Монолит или небольшое количество сервисов
- Нужен контроль над сессиями (kill session, list active sessions)
- Критично важна возможность немедленного отзыва
- Невысокие требования к latency

---

## Вариант B: JWT (stateless)

### Как работает
```
Login → Server выпускает JWT (подписанный токен)
Каждый запрос → Client отправляет JWT в Authorization header
Server проверяет подпись (не нужен lookup)
```

### Преимущества
- **Не нужно хранилище** — вся информация в токене
- **Быстрее** — нет lookup в Redis/DB
- **Легко масштабировать** — любой сервис может проверить токен
- **Меньше инфраструктуры** — не нужен Redis для сессий
- **Проще для микросервисов** — каждый сервис сам проверяет

### Недостатки
- **Нельзя отозвать** — токен живёт до expiry
- **Сложный logout** — нужно вести blacklist (черновик-лист убивает stateless)
- **Payload не секретный** — JWT подписан, но не зашифрован (base64)
- **Размер** — больше, чем session ID (может быть проблема для cookie)
- **Сложности с secure storage на клиенте** — localStorage уязвим для XSS

### Когда выбирать
- Микросервисная архитектура
- Нет общего хранилища между сервисами
- Высокие требования к производительности
- Низкие требования к возможности отзыва сессий

---

## Decision Framework

### Вопросы, которые помогут выбрать:

1. **Нужен ли мгновенный отзыв сессий?**
   - Да → Session
   - Нет → JWT

2. **Сколько сервисов проверяют токен?**
   - Один → Session (дешевле)
   - Много → JWT (меньше инфраструктуры)

3. **Есть ли уже Redis в инфраструктуре?**
   - Да → Session
   - Нет → JWT

4. **Насколько критична latency?**
   - Критична → JWT
   - Некритична → Session

5. **Какой тип приложения?**
   - SPA/мобильное приложение → JWT
   - Server-rendered pages → Session

## Компромисс: Hybrid approach

Современный подход, сочетающий преимущества обоих:

```
Access Token (JWT) — короткий (5-15 минут), stateless
Refresh Token (long-lived) — в HttpOnly Cookie, может быть отозван
```

| Компонент | Живёт | Stateful? | Хранение |
|-----------|-------|-----------|----------|
| Access Token | 5-15 мин | Нет | Memory (JS) |
| Refresh Token | Дни/недели | Да (Redis) | HttpOnly Cookie |

### Почему это работает

- **Access Token короткий** — даже если украден, живёт недолго
- **Refresh Token можно отозвать** — logout = удалить refresh token из Redis
- **Refresh Token в HttpOnly Cookie** — защищён от XSS
- **Access Token в памяти** — не в localStorage, защищён от XSS

### Недостатки гибрида
- Сложнее реализовать
- Нужен Redis для refresh tokens
- Race conditions при refresh (нужен token rotation)

## Пример из жизни

**Ситуация:** Микросервисное приложение, 10+ сервисов, нужен SSO.

**Решение:** JWT + Refresh Token.

**Почему:**
- 10 сервисов → если все будут ходить в Redis на каждый запрос → latency
- JWT может проверить любой сервис без общего хранилища
- SSO → центральный Identity Provider выдаёт JWT

**Чем пожертвовали:**
- Нельзя мгновенно разлогинить пользователя (токен живёт 15 минут)
- Нужен механизм blacklist для экстренных случаев (компрометация)
