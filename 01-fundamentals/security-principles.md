# Threat Modeling

## Теория

Threat Modeling — это систематический процесс выявления, документирования и смягчения угроз безопасности на этапе проектирования.

> "Threat Modeling is the process of thinking about what could go wrong and deciding what to do about it." — Adam Shostack

## Как разработчик может ошибиться

- Не проводить Threat Modeling вообще ("у нас agile, нет времени")
- Проводить формально — "чтобы было", без реального анализа
- Думать, что SAFT/DAST заменяют Threat Modeling
- Документировать угрозы, но никогда не возвращаться к ним

## Как AppSec проводит Threat Modeling

### Мой процесс

```
1. Собрать контекст: что за система, кто пользователи, какие данные
2. Построить DFD: кто с кем общается
3. Определить trust boundaries
4. Применить STRIDE к каждому элементу DFD
5. Построить Attack Trees для критических путей
6. Оценить риски и recommended controls
7. Задокументировать результат
8. Отслеживать до закрытия
```

### Что спрашивать Product Owner / Архитектора

- "Какие данные обрабатывает система? Какой уровень чувствительности?"
- "Кто пользователи? Какие роли?"
- "С какими внешними системами интегрируется?"
- "Где хранятся данные?"
- "Какие compliance требования? (GDPR, PCI DSS, 152-ФЗ)"

### Что спрашивать разработчиков

- "Как реализована аутентификация?"
- "Как проверяется авторизация?"
- "Какие библиотеки используете для шифрования?"
- "Как обрабатываете ошибки?"
- "Где хранятся secrets?"

## Как исправить

Threat Modeling не исправляет — он **предотвращает**.
Исправление — это реализация контрмер для каждой найденной угрозы.

## Как предотвратить

- Сделать Threat Modeling частью Definition of Done
- Легковесный подход (30-60 минут) для небольших фич
- Полный Threat Modeling (2-4 часа) для архитектурных изменений
- Хранить результаты рядом с кодом (docs/threat-modeling/)

## Как оформить результат

```markdown
# Threat Model: Feature X

## Context
[Описание фичи]

## DFD
[Диаграмма]

## Threats

| ID | STRIDE | Threat | Risk | Control | Status |
|----|--------|--------|------|---------|--------|
| TM-001 | S | Spoofing user | High | MFA + JWT validation | Mitigated |
| TM-002 | I | Data leak via error | Medium | Generic error messages | In progress |
```

## Практика

**Из опыта**: Threat Modeling проводили для архитектурных изменений.
Формат: 1-2 сессии с архитектором и lead developer.
Основная сложность — не уйти в "паралич анализа".

**Лучшая практика**: начать с простого STRIDE для 3-4 ключевых элементов.
Лучше shallow Threat Modeling за 30 минут, чем глубокий — никогда.

## Lessons Learned

- Threat Modeling — самый эффективный инструмент AppSec (ROI выше, чем SAFT + DAST вместе)
- Легковесный подход > Идеальный подход (который никогда не сделают)
- Результаты нужно отслеживать, иначе Threat Modeling превращается в формальность
- Developer buy-in критичен — если разработчики не вовлечены, анализ будет поверхностным

### Теория
Не полагаться на один слой защиты. Если один механизм обойдён, следующий должен остановить атаку.

### Как разработчик может ошибиться
- "У нас есть CSP, поэтому XSS не страшен" — и перестать экранировать вывод
- "Мы используем HTTPS, поэтому всё безопасно" — и не шифровать данные в БД
- "Пароль хэшируется, поэтому input validation не нужен"

### Как AppSec обнаружит
- **Threat Modeling**: анализ single point of failure
- **Code Review**: отсутствие одного из слоёв защиты
- **Review архитектуры**: "а что, если WAF обойдут?"

### Как исправить
```
Layer 1: Input validation + encoding
Layer 2: CSP + HttpOnly cookies
Layer 3: WAF
Layer 4: Rate limiting
Layer 5: Monitoring + alerting
```

### Как предотвратить
- В threat modeling проверять: что, если каждый слой будет обойдён?
- В security review: checklist на defense in depth

### Lessons Learned
- Один слой защиты неизбежно будет обойдён. Вопрос времени.
- CSP — это не причина перестать экранировать XSS.
- Defense in depth = базовый уровень для production.

## Secure by Default

### Теория
Система должна быть безопасной "из коробки". Пользователь должен сознательно *понижать* безопасность, а не *повышать*.

### Как разработчик может ошибиться
- CORS: `Access-Control-Allow-Origin: *` по умолчанию
- Debug mode включён в production
- Default пароль admin/admin
- TLS отключён, пока не "настроим позже"

### Как AppSec обнаружит
- **SAST**: поиск insecure defaults
- **DAST**: проверка заголовков, TLS, debug endpoints
- **Review config**: дефолтные значения

### Как исправить
```nginx
# По умолчанию запрещено, потом разрешаем конкретные origin
add_header Access-Control-Allow-Origin "https://app.example.com";
```

### Как предотвратить
- Checklist дефолтных конфигов
- Security baseline для всех проектов
- Автоматические проверки в CI/CD

### Lessons Learned
- Insecure by default — самая дорогая ошибка. Ломает сразу всё.
- Разработчики не меняют дефолты. Если по умолчанию небезопасно — так и останется.

## Fail Secure

### Теория
При ошибке система должна переходить в безопасное состояние, а не открывать доступ.

### Как разработчик может ошибиться
```python
# УЯЗВИМО: если проверка упадёт — доступ будет разрешён
try:
    check_permission(user, resource)
except Exception:
    pass  # ❌ ошибка → доступ есть
```

### Как исправить
```python
# ✅ БЕЗОПАСНО: при ошибке доступ запрещён
if not check_permission(user, resource):
    abort(403)
```

### Lessons Learned
- Всегда проверяй: что будет, если этот код упадёт с ошибкой?
- Правило: deny by default на все случаи, кроме явного allow.

## Complete Mediation

### Теория
Проверка доступа должна происходить при каждом обращении к ресурсу, а не однажды (например, при логине).

### Как разработчик может ошибиться
- Сохранить `isAdmin: true` в сессии при логине и не проверять больше
- JWT с ролью, но без проверки на каждом endpoint

### Как исправить
- Проверять права на каждый запрос, не кэшировать решение
- Использовать Policy Engine (OPA, Casbin) для централизованной проверки

### Lessons Learned
- Роль при логине — не гарантия, что права не отозвали.
- Проверка должна быть на каждый запрос.
