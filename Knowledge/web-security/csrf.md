# CSRF (Cross-Site Request Forgery)

> Атака, при которой злоумышленник заставляет браузер жертвы отправить доверенный запрос на сервер.
>
> **Ключевая идея:** сервер доверяет запросу, потому что браузер автоматически прикладывает Cookie пользователя.

---

## Как работает атака

```
Пользователь входит в bank.com
          │
          ▼
Браузер получает SESSION Cookie
          │
          ▼
Пользователь открывает evil.com
          │
          ▼
evil.com автоматически отправляет POST-запрос на bank.com
          │
          ▼
Браузер автоматически прикладывает SESSION Cookie
          │
          ▼
Сервер считает запрос легитимным
          │
          ▼
Действие выполняется (перевод, смена email и т.д.)
```

### Что использует злоумышленник?

- [NO] Не пароль
- [NO] Не JWT
- [NO] Не Cookie

[OK] **Злоумышленник использует браузер пользователя**, который автоматически отправляет Cookie.

---

## Почему CORS не защищает от CSRF

Важно разделять две вещи:

### CORS

Отвечает на вопрос: **«Может ли JavaScript прочитать ответ другого Origin?»**

```javascript
fetch("https://bank.com/api/profile")
```

Без разрешения CORS:
- запрос **отправится**
- сервер **его обработает**
- JavaScript **не получит доступ к ответу**

### CSRF

Злоумышленнику **не нужен ответ**. Ему важно:

```
POST /transfer
```

Если перевод выполнен — атака уже успешна.

---

## SOP vs CORS vs CSRF

| Механизм | За что отвечает |
|----------|-----------------|
| **Same-Origin Policy (SOP)** | Запрещает JavaScript читать данные другого Origin |
| **CORS** | Разрешает/запрещает JavaScript читать ответы API |
| **CSRF-защита** | Проверяет, что запрос действительно инициировал доверенный клиент |

---

## Аналогия с офисом

| Механизм | Аналогия |
|----------|----------|
| **SOP** | Секретарь не разрешает постороннему читать документы директора |
| **CORS** | Секретарь выдаёт документы только доверенным организациям |
| **CSRF** | Злоумышленник приносит письмо директору. Секретарь видит: «На письме есть действительная печать (Cookie)» — и передаёт его. Секретарь **не проверяет**, кто составил письмо |

## Почему JWT в localStorage устраняет классический CSRF

HTML-форма умеет отправлять:

```html
<form action="https://bank.com/api" method="POST">
```

Но **не умеет** добавлять произвольные HTTP-заголовки, например:

```
Authorization: Bearer eyJ...
```

Заголовок `Authorization` добавляет **JavaScript приложения**:

```javascript
const token = localStorage.getItem("jwt");

fetch("/api", {
    headers: {
        Authorization: `Bearer ${token}`
    }
});
```

Код с `evil.com`:
- не может прочитать `localStorage` другого Origin
- не может добавить заголовок `Authorization`

Поэтому **обычная HTML-форма не сможет выполнить авторизованный запрос**.

## Где хранить токены?

### Cookie

| Плюсы | Минусы |
|-------|--------|
| Поддерживаются браузером | Требуют защиты от CSRF |
| Можно использовать `HttpOnly` | |
| JavaScript не может прочитать токен | |

### localStorage

| Плюсы | Минусы |
|-------|--------|
| Простой доступ | Любой XSS может украсть токен |
| Сохраняется после закрытия браузера | |

### sessionStorage

Живёт **только пока открыта вкладка**. После закрытия — очищается.

От XSS практически не защищает.

### Memory (переменная в JavaScript)

Токен хранится только в оперативной памяти JS-приложения:

```javascript
const [token, setToken] = useState(null);

// или

const auth = {
    token: jwt
}
```

| Особенности | Риски |
|-------------|-------|
| Исчезает после F5 | Если XSS выполняется во время активной сессии — токен доступен |
| Исчезает после закрытия вкладки | |
| Не сохраняется в браузере | |

## Современная схема аутентификации SPA

```
Login
    │
    ▼
Backend
    │
    ┌───────────┴───────────┐
    ▼                       ▼
Access Token          Refresh Token
(5–15 минут)          (7–30 дней)
    │                       │
    ▼                       ▼
Memory               HttpOnly Cookie
```

### При истечении Access Token

```
Memory
    │
    ├─ Access Token expired
    │
    ▼
POST /refresh
    │
    ├─ Browser автоматически отправляет Refresh Cookie
    │
    ▼
Backend проверяет Refresh Token
    │
    ▼
Выдаёт новый Access Token
    │
    ▼
React сохраняет в Memory
```

### Почему Access Token делают короткоживущим?

Если Access Token украден:
- срок его действия ограничен (например, 5–15 минут)
- злоумышленник не сможет использовать его долго

### Почему Refresh Token хранят в HttpOnly Cookie?

Потому что это **самый ценный токен**. Настройки обычно включают:

| Флаг | Назначение |
|------|------------|
| `HttpOnly` | JavaScript не может прочитать Cookie |
| `Secure` | Передаётся только по HTTPS |
| `SameSite` | Снижает риск CSRF |

## Что важно помнить

> **Cookie ≠ небезопасно.**
> **JWT в localStorage ≠ автоматически безопасно.**
>
> Выбор зависит от архитектуры и модели угроз.

**Современный подход для SPA:**
- короткоживущий Access Token → **Memory**
- долгоживущий Refresh Token → **HttpOnly Cookie**

Это позволяет снизить последствия **как XSS, так и компрометации Access Token**.

---

## Что запомнить (коротко)

1. **CSRF использует браузер пользователя**, а не крадёт его учётные данные
2. **CORS защищает чтение ответов**, а не отправку запросов
3. **SOP запрещает JavaScript читать данные другого Origin**
4. **HTML-форма не может добавить заголовок `Authorization`**
5. `localStorage` и `sessionStorage` доступны JavaScript и **уязвимы при XSS**
6. **Memory** не сохраняет токен после перезагрузки страницы, но не защищает от активного XSS
7. Один из наиболее распространённых современных подходов — **Access Token в Memory + Refresh Token в HttpOnly Cookie**

| Тема | Связь |
|------|-------|
