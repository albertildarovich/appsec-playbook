# Security Misconfiguration

> Небезопасная конфигурация приложения, сервера, платформы или инфраструктуры, которая раскрывает лишнюю информацию или предоставляет злоумышленнику ненужные возможности.
>
> **Ключевое отличие:** в отличие от SQL Injection или XSS, проблема обычно не в коде, а в настройках.

---

## Главная идея

Самый важный вопрос AppSec-инженера:

> **«Почему это вообще доступно?»**

Не «как это защитить?», а **«нужно ли это в production?»**

---

## Типичные примеры

### 1. Открытый Swagger

```
https://company.com/swagger
```

**Почему опасно:**
- Раскрывает внутренние API
- Показывает методы, параметры, схемы данных
- Облегчает разведку злоумышленнику

**Защита:**
- Отключить в production
- Ограничить доступ VPN или администраторами

---

### 2. Debug Mode в production

**Опасности:**
- Подробные ошибки
- Внутренние логи
- Дополнительная диагностическая информация
- Иногда тестовые endpoint'ы

**Защита:**
```
DEBUG = OFF
```

---

### 3. Stack Trace пользователю

```
NullPointerException
  at UserService.java:154
  ...
Spring Boot 3.2.1
Hibernate 6.5
```

**Что узнаёт злоумышленник:**
- Архитектуру приложения
- Названия классов
- Номера строк
- Используемые технологии
- Версии библиотек

**Защита:**
- Показывать пользователю только `500 Internal Server Error`
- Подробности писать только в серверные логи

---

### 4. Заголовок Server

```
Server: Apache Tomcat 9.0.17
```

**Почему плохо:**
- Раскрывает используемые технологии
- Позволяет искать известные CVE

**Защита:**
- Убрать или минимизировать заголовок
- Не раскрывать версии ПО без необходимости

---

### 5. Доступный `.git`

```
/.git/
```

**Злоумышленник может получить:**
- Исходный код
- Историю коммитов
- Удалённые секреты (попавшие в коммиты)
- Архитектуру проекта
- Информацию об авторах

**Защита:**
- Никогда не размещать `.git` в директории, доступной через веб-сервер

---

### 6. Доступный `.env`

**Может содержать:**
- Пароли к БД
- JWT Secret
- API Keys
- AWS Keys
- SMTP Credentials
- Redis Password

**Последствия:**
- Практически полная компрометация приложения

**Защита:**
- `.env` никогда не должен быть доступен через HTTP

---

### 7. Стандартные учётные данные

```
admin / admin
root / root
```

Одна из самых распространённых ошибок конфигурации.

---

### 8. Ненужные сервисы, доступные извне

- Tomcat Manager
- Jenkins
- Grafana
- Kibana
- Prometheus
- Spring Actuator
- PHPMyAdmin

**Принцип:** если они не нужны пользователям — они не должны быть доступны извне.

---

## Какие принципы нарушаются

### Конфиденциальность (CIA)

Мы раскрываем:
- Секреты
- Архитектуру
- Версии ПО
- Внутреннюю структуру приложения

### Secure by Default

Система должна быть безопасной сразу после установки.

По умолчанию должно быть:
- `DEBUG = OFF`
- Swagger = OFF
- Тестовые endpoint'ы = OFF
- Стандартные пароли отсутствуют

### Уменьшение поверхности атаки (Reduce Attack Surface)

> **Лучший способ защиты: не публиковать ненужную функциональность.**

## Что искать на Code Review

Хотя уязвимость часто относится к конфигурации, в коде стоит обратить внимание на:

```bash
# Поиск debug-кода
grep -rn "DEBUG\|debug\|printStackTrace\|System.out" src/ --include="*.java" --include="*.py"

# Поиск stack trace
grep -rn "printStackTrace\|traceback.print_exc\|console.trace" src/ --include="*.java" --include="*.py" --include="*.js"

# Поиск тестовых endpoint'ов
grep -rn "test\|health\|diagnostic\|actuator" src/ --include="*.java" --include="*.py" --include="*.js"

# Поиск логирования секретов
grep -rn "password\|secret\|key\|token\|credential" src/ --include="*.properties" --include="*.yaml" --include="*.yml" --include="*.json"
```

---

## Что искать при Security Review

- Открытый Swagger
- Открытый `.git`
- Открытый `.env`
- Страницы ошибок (stack trace)
- DEBUG Mode
- Server Header
- Тестовые аккаунты
- Стандартные пароли
- Лишние открытые сервисы
- Default credentials
- Скрытые endpoint'ы
- Панели управления, доступные извне

---

## Может ли SAST найти?

**Частично.**

SAST способен обнаружить:
- Вывод stack trace
- Логирование секретов
- Debug-код
- Тестовые endpoint'ы

Но большинство проблем Security Misconfiguration выявляются:
- **Security Review** — ручной аудит конфигурации
- **Configuration Review** — проверка настроек
- **Infrastructure Audit** — аудит инфраструктуры
- **DAST** — динамическое тестирование
- **Ручное тестирование** — pentest

## Что любят спрашивать на интервью

| Вопрос | Ответ |
|--------|-------|
| **Что такое Security Misconfiguration?** | Небезопасная конфигурация приложения или инфраструктуры, которая раскрывает информацию или предоставляет лишние возможности злоумышленнику |
| **Приведите примеры** | DEBUG Mode, открытый Swagger, доступный `.git`, доступный `.env`, стандартные пароли, подробные stack trace, раскрытие версий ПО |
| **Как защититься?** | Secure by Default. Минимизировать поверхность атаки. Не раскрывать лишнюю информацию. Регулярно проводить аудит конфигурации. Использовать безопасные настройки для production |
| **Чем отличается от других уязвимостей?** | Проблема не в коде, а в настройках. Система сама «помогает» злоумышленнику, раскрывая информацию или предоставляя доступ |

## Главная мысль

Если в предыдущих темах злоумышленник **заставлял систему делать что-то опасное**, то здесь **система сама бесплатно помогает злоумышленнику**.

> **Самый важный вопрос AppSec-инженера: «Почему это вообще доступно?»**

Именно этот вопрос объединяет практически все примеры Security Misconfiguration.

---

## Что запомнить (коротко)

1. **Security Misconfiguration** — небезопасные настройки, а не код
2. **Secure by Default** — система должна быть безопасной «из коробки»
3. **Reduce Attack Surface** — не публикуй то, что не нужно
4. **Главный вопрос:** «Почему это вообще доступно?»
5. **Разведка** — злоумышленник получает информацию бесплатно
