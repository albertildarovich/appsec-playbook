# Vulnerable and Outdated Components

> Использование уязвимых или устаревших библиотек, фреймворков и зависимостей, которое может привести к компрометации приложения.
>
> **Ключевая идея:** наличие CVE ≠ наличие риска. AppSec оценивает именно **риск эксплуатации**, а не количество CVE.

---

## Основная идея

Приложения редко пишутся с нуля. Они используют десятки, сотни, а иногда и тысячи зависимостей:
- Библиотеки (Apache Commons, Log4j, Jackson)
- Фреймворки (Spring, Django, Express)
- Инструменты сборки (Maven, npm, pip)
- Базовые образы Docker
- Системные пакеты (OpenSSL, libcurl)

**Каждая зависимость — это потенциальная поверхность атаки.**

---

## Как выглядит процесс

```
SCA
  ↓
Находит CVE
  ↓
Triage (FP? Reachable? Exploit?)
  ↓
Risk Assessment
  ↓
Remediation / Risk Acceptance / Mitigation
```

---

## CVE, CVSS, Risk — нужно различать

### CVE (Common Vulnerabilities and Exposures)

Идентификатор уязвимости.

```
CVE-2021-44228  (Log4Shell)
CVE-2023-46604  (ActiveMQ)
```

### CVSS (Common Vulnerability Scoring System)

Техническая критичность — оценка от 0 до 10.

```
CVSS: 9.8  → Critical
CVSS: 7.5  → High
```

### Реальный риск

Зависит от контекста:

| Фактор | Влияние |
|--------|---------|
| **Internet Facing** | Уязвимость доступна извне? |
| **Reachability** | Используется ли уязвимый код? |
| **Business Criticality** | Насколько критичен сервис? |
| **KEV** (Known Exploited Vulnerabilities) | Есть ли эксплойт в реальных атаках? |
| **Public PoC** | Есть ли публичный эксплойт? |
| **Compensating Controls** | Есть ли WAF, сегментация, sandbox? |

> Пример: библиотека содержит уязвимый XML Parser, но приложение работает только с JSON. CVSS может быть 9.8, но реальный риск — низкий.

---

## Reachability — главный вопрос AppSec

> **Используется ли вообще уязвимый код?**

Библиотека может быть в classpath / `node_modules`, но:
- Уязвимый класс может никогда не вызываться
- Функция может быть недоступна из пользовательского ввода
- Уязвимость может требовать специфических условий

Без анализа reachability невозможно оценить реальный риск.

---

## Triage

После получения отчёта SCA необходимо:

1. **Убрать False Positive** — CVE может не затрагивать используемую версию
2. **Проверить Reachability** — вызывается ли уязвимый код?
3. **Проверить Public Exploit** — есть ли PoC в открытом доступе?
4. **Проверить KEV** — используется ли CISA Known Exploited Vulnerabilities?
5. **Оценить Internet Facing** — доступен ли сервис извне?
6. **Оценить бизнес-критичность** — что будет, если сервис скомпрометируют?

---

## Почему нельзя исправлять всё подряд

Не существует команды:

```
Fix All CVE ✅   ← не работает
```

Всегда производится **приоритизация**.

### Пример

| CVE | CVSS | Internet Facing | Reachability | KEV | Приоритет |
|-----|------|----------------|-------------|-----|-----------|
| CVE-2024-XXX | 7.2 | ✅ | ✅ | ✅ | **CRITICAL** → немедленно |
| CVE-2024-YYY | 9.8 | ❌ Internal | ❌ Not reachable | ❌ | **LOW** → в бэклог |

> **Лучше исправить:** CVSS 7.2, Internet, KEV, Reachable
>
> **Чем:** CVSS 9.8, Internal, No Reachability

---

## Стратегии управления рисками

| Стратегия | Описание |
|-----------|----------|
| **Mitigate** | Исправить — обновить версию, заменить библиотеку |
| **Accept** | Принять риск — если CVE не reachable и low impact |
| **Transfer** | Передать — например, переложить на облачного провайдера (AWS RDS вместо своего PostgreSQL) |
| **Avoid** | Избежать — удалить зависимость, переписать функциональность |

---

## Если обновить библиотеку нельзя

Бывает, что:
- Нет patched версии (vendors не выпустили фикс)
- Обновление ломает API (breaking changes)
- Зависимость транзитивная и не управляется напрямую

**Компенсирующие меры (compensating controls):**

| Мера | Пример |
|------|--------|
| **WAF** | Блокировать атаки на уровне HTTP |
| **Network Segmentation** | Ограничить доступ к сервису извне |
| **Least Privilege** | Минимизировать права процесса |
| **Sandbox / Container Isolation** | Ограничить возможности контейнера |
| **API Gateway** | Централизованная фильтрация |
| **Feature Disable** | Отключить уязвимую функцию |
| **Monitoring** | Усилить логирование на признаки эксплуатации |

## SBOM (Software Bill of Materials)

**SBOM** — это инвентаризация компонентов приложения.

Отвечает на вопрос:
> **Что входит в приложение?**

Форматы: **SPDX**, **CycloneDX**, **SWID**.

Что содержит:
- Названия пакетов
- Версии
- Лицензии
- Транзитивные зависимости

> Сам по себе SBOM **не показывает CVE**. Это просто список того, что есть.

---

## Trivy

**Trivy** — анализатор безопасности с открытым исходным кодом.

Отвечает на вопрос:
> **Какие компоненты уязвимы?**

Анализирует:
- Зависимости (Java, Python, JS, Go, Ruby, PHP, .NET, Rust)
- Контейнеры (Docker образы)
- Секреты
- Kubernetes (манифесты)
- Misconfiguration (Terraform, CloudFormation)
- SBOM

### Разница SBOM и Trivy

```
SBOM
  ↓
Список компонентов
  ↓
(не показывает CVE)

Trivy
  ↓
Анализ компонентов
  ↓
Показывает CVE и misconfiguration
```

## CI/CD — автоматизация поиска

Лучше искать проблемы автоматически, а не вручную.

```
Push
  ↓
Pull Request
  ↓
SCA ← Trivy / Snyk / Dependabot
  ↓
SAST ← Semgrep / CodeQL
  ↓
Secrets ← TruffleHog / Gitleaks
  ↓
Merge
```

### Continuous Scanning

Безопасность проверяется постоянно:

- **Pull Request** — проверка новых зависимостей
- **Build** — сканирование артефактов
- **Release** — финальная проверка перед релизом
- **После появления новых CVE** — пересканирование существующих артефактов

## Что любят спрашивать на интервью

| Вопрос | Ответ |
|--------|-------|
| **Что делать, если библиотеку нельзя обновить?** | Компенсирующие меры: WAF, сегментация, sandbox, feature disable, мониторинг |
| **Чем SBOM отличается от Trivy?** | SBOM — список компонентов (что есть), Trivy — анализ уязвимостей (что опасно) |
| **Что такое Reachability?** | Используется ли уязвимый код в приложении |
| **Что такое Triage?** | Процесс оценки CVE: FP, reachability, exploit, KEV, контекст |
| **Почему CVSS ≠ Risk?** | CVSS — техническая оценка, Risk зависит от контекста (Internet Facing, Reachability, бизнес-критичность) |
| **Как построить процесс SCA?** | CI/CD → SCA → Triage → Risk Assessment → Remediation / Acceptance → Continuous Scanning |
| **Что такое KEV?** | CISA Known Exploited Vulnerabilities — список уязвимостей, используемых в реальных атаках |

---

## Что запомнить (коротко)

1. **CVE ≠ Risk** — оценивай контекст, а не только CVSS
2. **Reachability** — главный вопрос AppSec: используется ли уязвимый код?
3. **Triage** — всегда убирай FP, проверяй reachability и KEV
4. **Compensating Controls** — если нельзя обновить, изолируй
5. **SBOM** — что входит в приложение (не показывает CVE)
6. **Trivy** — что уязвимо в приложении
7. **Continuous Scanning** — безопасность проверяется постоянно, а не разово
