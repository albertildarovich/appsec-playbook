# Insecure Deserialization

> Уязвимость, возникающая, когда приложение десериализует данные, контролируемые пользователем, без должной проверки.
>
> **Главная проблема:** злоумышленник начинает управлять процессом создания объектов.
>
> **Важно: это не проблема Java, а класс уязвимостей, общий для многих языков.**

---

## Что такое сериализация и десериализация

**Сериализация** — преобразование объекта в последовательность байтов (или другой формат) для хранения или передачи по сети.

```
Объект
  ↓
Сериализация
  ↓
Байты / JSON / XML
```

**Десериализация** — обратный процесс — восстановление объекта из данных.

```
Байты / JSON / XML
  ↓
Десериализация
  ↓
Объект
```

---

## Что такое Insecure Deserialization

Ситуация, когда приложение **без проверки** десериализует данные, полностью контролируемые пользователем.

```java
// [NO] ОПАСНО — Java
ObjectInputStream in = new ObjectInputStream(request.getInputStream());
User user = (User) in.readObject();
```

Здесь приложение **доверяет входным данным** и восстанавливает из них объект.

---

## Insecure Deserialization в разных языках

Проблема **не относится только к Java**. Любой язык, где десериализация может выполнять код или вызывать методы объектов, — потенциально опасен.

### Java

```java
// [NO] Классическая проблема: ObjectInputStream.readObject()
ObjectInputStream in = new ObjectInputStream(request.getInputStream());
Object obj = in.readObject();  // может восстановить ЛЮБОЙ объект
```

Исторически в Java было огромное количество RCE через gadget chains.

### Python — pickle

```python
# [NO] ОПАСНО — аналог Java Serialization
import pickle
data = pickle.loads(request.body)  # может выполнить произвольный код
```

`pickle` способен выполнять произвольный код при восстановлении объекта.
**Правило:** никогда не вызывайте `pickle.loads()` на данных от пользователя.

### PHP — unserialize()

```php
// [NO] ОПАСНО — одна из самых известных функций в мире AppSec
$user = unserialize($_POST['data']);
```

Через «магические методы» (`__wakeup()`, `__destruct()`, `__toString()`) можно получить выполнение нежелательного кода. Очень много CVE связано именно с `unserialize()`.

### .NET (C#) — BinaryFormatter

```csharp
// [NO] ОПАСНО — Microsoft официально не рекомендует
BinaryFormatter formatter = new BinaryFormatter();
object obj = formatter.Deserialize(stream);
```

### Ruby — Marshal / YAML

```ruby
# [NO] ОПАСНО
data = Marshal.load(user_input)
data = YAML.load(user_input)  # тоже опасно
```

### Go — JSON.Unmarshal (безопасно)

```go
// [OK] БЕЗОПАСНО — просто заполняет поля структуры, без выполнения кода
var user User
err := json.Unmarshal(jsonData, &user)
```

Go в этом плане намного безопаснее.

### Rust — serde_json (безопасно)

```rust
// [OK] БЕЗОПАСНО — просто создаёт структуру, никакой магии
let user: User = serde_json::from_str(json_data)?;
```

## Почему это опасно

Главная проблема **не в данных**. Главная проблема в том, что злоумышленник начинает **управлять процессом создания объектов**.

Приложение говорит:
> «Я доверяю этим байтам. Создай из них объект.»

Вопрос в том, насколько «умной» является десериализация:
- **Java** (`ObjectInputStream`) — может восстановить практически любой объект, вызывая его методы
- **Python** (`pickle`) — может выполнить произвольный код
- **PHP** (`unserialize`) — вызывает магические методы
- **Go** (`json.Unmarshal`) — просто заполняет поля структуры, не выполняя код
- **Rust** (`serde_json`) — просто создаёт структуру, не выполняя код

---

## Что такое Gadget Chain

**Gadget Chain** — цепочка уже существующих классов приложения или библиотек, которая при десериализации приводит к выполнению опасных действий.

> [WARN] Важно: злоумышленник **не загружает свой класс**. Он использует классы, которые **уже присутствуют** в приложении или его зависимостях.

### Возможные последствия

- Remote Code Execution (RCE)
- Чтение файлов
- Выполнение системных команд
- Сетевые обращения (SSRF)
- Отказ в обслуживании (DoS)

---

## Почему JSON безопаснее

Обычный JSON выглядит так:

```json
{ "name": "Alex", "age": 30 }
```

Здесь **нет информации**:
- Какой класс создавать
- Какие методы вызвать
- Какие конструкторы запустить

Он просто говорит: `name = Alex`, `age = 30`.

Jackson обычно работает так:

```java
// [OK] Приложение само определяет тип
User user = mapper.readValue(json, User.class);
```

То есть приложение само определяет, какой объект создавать.

### Когда JSON становится опасным

Если разработчик говорит Jackson: *«Пользователь сам укажет, какой класс создавать»* — и включает полиморфную десериализацию:

```java
// [NO] ОПАСНО — enableDefaultTyping
ObjectMapper mapper = new ObjectMapper();
mapper.enableDefaultTyping();  // разрешает @class
```

Тогда проблема снова появляется:

```json
{ "@class": "java.lang.Runtime", ... }
```

---

## Ключевое правило

> [NO] **Неверно:** «Insecure Deserialization — проблема Java»
>
> [OK] **Верно:** Insecure Deserialization возникает в любой технологии, где приложение позволяет **недоверенным данным управлять процессом восстановления объектов**.

---

## Почему эта тема сложнее других

Все предыдущие уязвимости были очень наглядными:

| Уязвимость | Что видит защитник |
|-----------|-------------------|
| SQL Injection | Видишь SQL-запрос |
| XSS | Видишь JavaScript |
| SSRF | Видишь HTTP-запрос |
| Command Injection | Видишь командную строку |

А в Insecure Deserialization:
> «Ну создали какой-то объект... и что?»

Опасность не в данных, а в **поведении механизма десериализации**. Это интерпретатор, который восстанавливает объектный граф, и злоумышленник управляет этим процессом.

---

## Как защищаться

### 1. Не использовать опасные механизмы десериализации для данных от пользователя

Это **современная рекомендация** большинства специалистов по безопасности.

- Java: не используйте `ObjectInputStream` с пользовательскими данными
- Python: не используйте `pickle.loads()` с пользовательскими данными
- PHP: не используйте `unserialize()` с пользовательскими данными
- .NET: не используйте `BinaryFormatter.Deserialize()`
- Ruby: не используйте `Marshal.load()`

### 2. Использовать безопасные форматы

- JSON
- Protocol Buffers (Protobuf)
- Avro

### 3. Десериализовать только в заранее известные типы

```java
// [OK] БЕЗОПАСНО — известный тип
mapper.readValue(json, User.class);

// [NO] ОПАСНО — пользователь выбирает тип
mapper.readValue(json, Class.forName(userInput));
```

### 4. Минимизировать поверхность атаки

Не принимать сериализованные объекты там, где достаточно обычных DTO или JSON.

### 5. Обновлять библиотеки

Многие исторические атаки были связаны с **уязвимыми версиями библиотек**, содержащими известные gadget chains (Apache Commons Collections, Jackson, Fastjson и др.).

---

## Может ли SAST найти проблему?

**Да, частично.** SAST способен обнаружить:
- использование `ObjectInputStream`
- вызовы `readObject()`
- `pickle.loads()`
- `unserialize()` в PHP
- `BinaryFormatter.Deserialize()`
- `enableDefaultTyping()` в Jackson

Но определить, существует ли реальная gadget chain и возможна ли эксплуатация, **только по коду обычно невозможно**.

## Что запомнить (коротко)

1. **Insecure Deserialization** — приложение доверяет пользовательским данным при восстановлении объектов
2. **Это не только Java** — Python (`pickle`), PHP (`unserialize`), .NET, Ruby — все могут быть уязвимы
3. **Gadget Chain** — злоумышленник использует существующие классы, не загружая свои
4. **JSON безопаснее** — тип объекта известен, строки не выполняются как код
5. **JSON опасен** — если включена полиморфная десериализация (`@class`, `enableDefaultTyping`)
6. **Лучшая защита** — не использовать опасные механизмы десериализации для пользовательских данных
7. **Обновлять библиотеки** — известные gadget chains часто фиксятся в новых версиях
