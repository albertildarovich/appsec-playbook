# Identification & Authentication Failures

> Уязвимости, связанные с идентификацией и аутентификацией пользователей.
>
> **Ключевая идея:** это не только проверка логина и пароля. Нужно оценивать весь жизненный цикл учётной записи.
>
> **В контексте всего OWASP Top 10:** сначала мы оцениваем безопасность зависимостей и процессов (A06 — Vulnerable Components), а затем — безопасность пользователей и сессий (A07). Обе темы объединяет общий подход: найти проблему → оценить риск → найти компромисс между безопасностью и бизнесом → автоматизировать.

---

## 1. Username Enumeration

### Проблема

Приложение позволяет определить, существует ли пользователь.

```http
[NO] Плохо:
POST /login → "User not found"
POST /login → "Wrong password"

[NO] Или:
POST /forgot-password → "Email sent"     # пользователь существует
POST /forgot-password → "User not found"  # пользователя нет
```

### Последствия

- Сбор списка пользователей
- Brute force по известным пользователям
- Phishing (знаем, кому писать)
- Credential stuffing (знаем, какие用户名 проверять)

### Защита

Одинаковые ответы независимо от существования пользователя:

```http
[OK] Хорошо:
POST /login → "Invalid credentials"

POST /forgot-password → "If the account exists, instructions have been sent."
```

---

## 2. Timing Attack

### Проблема

Даже если текст ответа одинаковый, время ответа может выдать существование пользователя.

```
Существующий пользователь   →  250 ms  (проверяем hash пароля)
Несуществующий пользователь →   20 ms  (сразу возвращаем ошибку)
```

### Защита

- Одинаковое время обработки для существующих и несуществующих пользователей
- Максимально одинаковая логика выполнения
- Rate limiting
- CAPTCHA

> [WARN] Важно: простая рандомизация времени не является надёжной защитой — при большом количестве запросов статистический анализ позволяет выявить различия.

---

## 3. Brute Force

Что проверяем:

- Есть ли ограничение количества попыток?
- Есть ли задержка между попытками?
- Есть ли CAPTCHA?
- Есть ли rate limiting (на IP, на аккаунт)?
- Есть ли временная блокировка?

---

## 4. Почему нельзя просто блокировать аккаунт?

Если после 5 ошибок аккаунт блокируется:

```
Account locked. Contact support.
```

Злоумышленник сможет заблокировать **любого пользователя**, просто подбирая пароль 5 раз для каждого логина.

Получится **DoS-атака на аккаунты**.

### Решение — баланс

| Метод | Описание |
|-------|----------|
| **Exponential backoff** | Задержка растёт с каждой попыткой: 1s → 2s → 4s → 8s → ... |
| **Rate limiting** | Ограничение по IP + по аккаунту |
| **CAPTCHA** | После N неудачных попыток |
| **MFA при подозрительной активности** | Не блокируем, но требуем второй фактор |
| **Account lock с ограничениями** | Только на короткое время (5–15 мин), автоматический unlock |

---

## 5. MFA

**Наличие MFA не означает безопасность.** Проверяем:

- Можно ли подобрать код? (6 цифр — 1M комбинаций, нет rate limiting?)
- Сколько живёт код? (30 мин — слишком долго)
- Можно ли использовать код повторно?
- Защищены ли процессы восстановления аккаунта?
- Защищены ли процессы смены телефона?
- Защищена ли система от **MFA Fatigue** (злоумышленник спамит push-уведомления, жертва устаёт и нажимает «Accept»)?

## 6. Недостатки SMS MFA

SMS — не самый надёжный второй фактор.

| Угроза | Описание |
|--------|----------|
| **SIM Swapping** | Злоумышленник убеждает оператора перенести номер на свою SIM |
| **SS7 атаки** | Перехват SMS через уязвимости протокола сигнализации |
| **Malware** | Вредоносное ПО на телефоне читает SMS |
| **Social Engineering** | Жертву убеждают назвать код |

### Лучшие альтернативы

| Метод | Надёжность |
|-------|-----------|
| **TOTP** (Google Authenticator, Authy) | Высокая — код генерируется на устройстве |
| **Push Authentication** | Высокая — жертва должна явно нажать «Approve» |
| **FIDO2 / WebAuthn** | Очень высокая — криптографические ключи, устойчиво к phishing |

## 7. Session Fixation

### Проблема

```
До логина:    SessionID = ABC123
После логина: SessionID = ABC123   ← НЕ ИЗМЕНИЛСЯ!
```

Если Session ID не изменился после аутентификации, злоумышленник может:
1. Заставить жертву перейти по ссылке с заранее известным Session ID
2. После того как жертва войдёт, использовать тот же Session ID

### Защита

После успешной аутентификации — **всегда** регенерировать Session ID:

```javascript
req.session.regenerate(() => {
    // сохраняем данные сессии
});
```

Современные фреймворки обычно делают это автоматически.

## 8. JWT и отзыв доступа

### Проблема

Пользователя отключили (уволен, заблокирован, удалён). Но Access Token уже выдан.

JWT:
- [OK] Проверяет подпись
- [OK] Проверяет `exp`
- [NO] **Не знает**, что пользователь отключён

### Последствия

До окончания срока действия токен остаётся рабочим.

```
Выдача:     10:00, Access Token exp = 10:15
Увольнение: 10:05
Токен жив:  до 10:15  ← 10 минут уязвимости
```

---

## 9. Refresh Token

Если не отозвать Refresh Token, пользователь сможет получать новые Access Token.

**Поэтому при Logout или Disable User:**
- Refresh Token необходимо инвалидировать (удалить из БД или добавить в blacklist)

---

## 10. Logout в JWT

Просто удалить токен из браузера **недостаточно**.

Если злоумышленник уже украл JWT, он сможет пользоваться им до окончания срока действия.

### Решения

| Метод | Описание |
|-------|----------|
| **Короткий Access Token** (5–15 мин) | Окно уязвимости минимально |
| **Blacklist** | Хранить отозванные токены (теряем stateless) |
| **Token version** | Версия токена в БД, проверять при каждом запросе |
| **Проверка статуса пользователя** | Каждый запрос проверяет `is_active` в БД (теряем stateless) |

---

## 11. Компромисс JWT

| [OK] JWT даёт | [NO] Но усложняет |
|------------|----------------|
| Stateless | Logout (как отозвать?) |
| Масштабируемость | Отзыв доступа (пользователя уволили) |
| Отсутствие хранения сессий на сервере | Немедленную блокировку |

> **Архитектура всегда строится исходя из требований бизнеса.**
> Если нужно мгновенно блокировать пользователей — возможно, JWT не лучший выбор, или нужен hybrid подход (короткие токены + черный список).

## 12. Risk-Based Authentication (RBA)

Современные системы оценивают риск входа.

### Факторы для оценки

- Device Fingerprint
- Геолокация
- IP-адрес
- ASN (провайдер)
- История входов
- Часовой пояс
- Браузер и ОС
- Скорость перемещения между странами

### Пример

```python
if risk_score > THRESHOLD:
    require_mfa()
else:
    allow_login()
```

### При высоком риске

- Запросить MFA
- Отправить email с подтверждением
- Временно ограничить действия

## Что любят спрашивать на интервью

| Вопрос | Ответ |
|--------|-------|
| **Почему SMS хуже TOTP?** | SIM Swapping, SS7, перехват SMS, malware |
| **Что такое Session Fixation?** | Session ID не меняется после логина, злоумышленник может навязать свой ID |
| **Почему Logout в JWT — сложная задача?** | JWT stateless — нельзя отозвать до истечения срока |
| **Что делать после увольнения пользователя?** | Отозвать Refresh Token, установить короткий Access Token, проверить token version |
| **Почему нельзя просто блокировать аккаунт после 5 ошибок?** | DoS — злоумышленник заблокирует любого пользователя |
| **Как защититься от Username Enumeration?** | Одинаковые ответы, одинаковое время обработки |
| **Почему одинакового текста ответа недостаточно?** | Timing attack — разница во времени может выдать существование пользователя |
| **Что такое MFA Fatigue?** | Злоумышленник спамит push-уведомлениями, жертва устаёт и нажимает Accept |

## Самое важное, что нужно запомнить

> **Идентификация и аутентификация — это не только проверка логина и пароля.**
>
> Нужно оценивать весь жизненный цикл учётной записи:
> - Вход
> - MFA
> - Управление сессией
> - Logout
> - Отзыв токенов
> - Восстановление пароля
> - Смену телефона
> - Блокировку пользователя
> - Мониторинг подозрительной активности

---

## Что запомнить (коротко)

1. **Username Enumeration** — одинаковые ответы + одинаковое время
2. **Timing Attack** — даже время ответа может быть информацией
3. **Brute Force** — блокировка аккаунта = DoS, нужен баланс (backoff, rate limit, CAPTCHA)
4. **MFA** — наличие ≠ безопасность, SMS — не лучший вариант (SIM Swap, SS7)
5. **Session Fixation** — регенерировать Session ID после логина
6. **JWT** — stateless, но сложный logout и отзыв доступа
7. **Refresh Token** — инвалидировать при logout / disable user
8. **Risk-Based Authentication** — оценивать контекст входа (device, geo, IP)

## * Главная мысль этих двух тем (A06 + A07)

За время этих блоков мы несколько раз пришли к одной и той же модели мышления, которая отличает сильных AppSec-инженеров:

> **Найти проблему → Понять риск → Оценить последствия → Предложить несколько вариантов защиты → Найти компромисс между безопасностью и бизнесом → Автоматизировать процесс**

Это не про отдельные уязвимости. Это про **архитектуру, процессы и управление рисками**.
