# Tool Selection — R&D как выбирать инструменты

> **Контекст:** на интервью спрашивают: «Как вы выбираете новый инструмент?». Ответ должен быть структурированным PoC-процессом, а не «ну, попробовал и понравилось».

---

## 1. Процесс выбора инструмента

```
Потребность -> PoC -> Сравнение -> FP/TP анализ -> Интеграция -> Стоимость -> Поддержка -> Решение
```

### Шаг 1: Потребность

Сформулировать, какую проблему решаем. Не «внедрим SAST», а:

- «Разработчики коммитят секреты в приватные репозитории»
- «У нас 200+ проектов, и мы не знаем, где используется Log4j»
- «SAST-сканер выдаёт 60% ложных срабатываний, команды не верят отчётам»

Без чёткой потребности выбор инструмента превращается в гадание.

### Шаг 2: PoC (Proof of Concept)

Ограниченный эксперимент на реальном коде:

- Берём 10-15 реальных проектов разных стеков
- Запускаем кандидатов одинаково (на одинаковых данных — same repo, same version)
- Фиксируем результаты: время сканирования, количество находок, ресурсы

### Шаг 3: Сравнение

Таблица сравнения кандидатов:

| Критерий | Инструмент A | Инструмент B | Вес |
|----------|-------------|-------------|-----|
| TP-rate | 85% | 92% | 0.3 |
| FP-rate | 25% | 12% | 0.3 |
| Время сканирования | 4 мин | 12 мин | 0.15 |
| Custom rules | YAML | QL | 0.15 |
| Стоимость | Free | $$$ | 0.05 |
| Поддержка сообщества | Отличная | Хорошая | 0.05 |

### Шаг 4: FP/TP анализ

Критический шаг — руками проверить находки:

```
100 находок сканера
-> 15 false positives (сантизация не распознана, контекст не учтён)
-> 85 true positives (реальные проблемы)
-> из них 10 критичных, 30 средних, 45 низких
```

Хороший инструмент: FP-rate < 20% и понятные правила, которые можно отключить/настроить.

### Шаг 5: Интеграция

- Как встраивается в CI/CD: SARIF, exit codes, API
- Работает ли с нашим GitLab/GitHub
- Нужен ли отдельный сервер или SaaS
- Как обрабатывает монорепозитории и полиглот

### Шаг 6: Стоимость

- Лицензия (per-seat, per-project, per-scan)
- Инфраструктура (self-hosted runner, БД, storage)
- Поддержка (SLA, время ответа)
- Обучение команды
- Стоимость ложных срабатываний: время разработчиков на разбор FP

### Шаг 7: Поддержка

- Частота обновления правил
- Сообщество (GitHub stars, issues, ответы)
- Roadmap проекта
- Активность мейнтейнеров

## 2. Пример: сравнение SAST-инструментов

```
Критерий           Semgrep   SonarQube   CodeQL
------------------ --------- ----------- ----------
Custom rules       YAML      GUI/PL/SQL  QL
Taint analysis     + (pro)   +           +++
Скорость           быстро    средне      медленно
FP-rate (наш код)  20%       15%         10%
Интеграция GitLab  отлично   хорошо      средне
Обучение           1 день    2-3 дня     1-2 недели
Стоимость          Free/Pro  CE/Enterprise Free (OSS)
```

Вывод: для нашего случая (GitLab, быстрые кастомные правила, маленькая команда) — Semgrep. CodeQL — если появится критичный сервис на Java/C#.

## 3. Пример: сравнение SCA-инструментов

```
Критерий           Trivy     Snyk       Grype
------------------ --------- ----------- ----------
Скорость           высокая   средняя     высокая
SBOM               CycloneDX  +          CycloneDX/SPDX
Лицензии           -         +          -
Интеграция с IDE   -         +          -
Fix PR             -         +          -
Стоимость          Free      Freemium   Free
Мониторинг         -         + (SaaS)   -
```

Вывод: Trivy для CI/CD и SBOM, Snyk — для разработчиков и фиксов.

## 4. Greenfield vs Brownfield

| | Greenfield (новый проект) | Brownfield (существующий) |
|---|---------------------------|---------------------------|
| Что важно | Лёгкая настройка, быстрый старт | Совместимость с legacy, миграция данных |
| Риск | Инструмент не масштабируется | Не работает на нашем стеке |
| Подход | Начинаем с малого, расширяем | Baseline текущих находок, поэтапное включение |

## 5. Оценка зрелости инструмента

| Признак | Молодой | Зрелый |
|---------|---------|--------|
| Версия | 0.x, частые breaking changes | 1.x+, стабильный API |
| Правила | 50-100 правил | 500+ правил |
| Сообщество | < 1k stars | 10k+ stars |
| Roadmap | Одна фича | Несколько направлений |
| Релизы | Еженедельные | Стабильный release cycle |

## 6. Interview Questions

| Вопрос | Ответ |
|--------|-------|
| Как выбираешь инструмент? | Потребность -> PoC на реальных проектах -> сравнение (TP/FP, скорость, стоимость) -> пилот -> раскатка. |
| Чем руководствуешься при сравнении? | TP/FP-rate на нашем коде, интеграция с CI/CD, стоимость владения, поддержка, обновление правил. |
| Что такое PoC в security? | Ограниченный эксперимент: реальный проект, реальный код, фиксируем метрики (время, находки, FP). Без PoC выбор — гадание. |
| Как понять, что инструмент не подходит? | FP-rate > 30%, нет интеграции с нашим CI, правила не обновляются, стоимость не окупается. |
| Как считать стоимость инструмента? | Лицензия + инфраструктура + обучение + время разработчиков на FP. Дешёвый инструмент с большим FP-rate обходится дороже. |
