# BOLA (Broken Object Level Authorization)

> Отсутствие проверки прав доступа пользователя к конкретному объекту при работе с API.
>
> **OWASP API Security Top 10: #API1 — Broken Object Level Authorization**

---

## Простое определение

Если API получает идентификатор объекта от клиента и **не проверяет**, имеет ли пользователь право работать с этим объектом, возникает BOLA.

```http
GET    /api/orders/15
PUT    /api/profile/25
DELETE /api/files/42
```

---

## Root Cause

**Главная причина:** backend доверяет идентификатору объекта, полученному от клиента, но не проверяет Object Authorization.

---

## BOLA и IDOR

По сути они описывают **одну и ту же проблему**. Разница — в контексте применения.

| | IDOR | BOLA |
|--|------|------|
| **Контекст** | Web Security (веб-приложения) | API Security (REST API, GraphQL, мобильные, микросервисы) |
| **Источник** | OWASP Top 10 (исторический) | OWASP API Security Top 10 (современный) |
| **Пример** | `GET /users/15` | `GET /api/users/15` или `PATCH /api/orders/15` |

---

## Почему JWT недостаточно

Проверка JWT подтверждает:
- пользователь аутентифицирован
- токен действителен
- известны роли и claims пользователя

**JWT не подтверждает**, что пользователь имеет право работать с конкретным объектом.

```json
{
  "sub": "123",
  "roles": ["USER"]
}
```

| Backend знает | Backend **не** знает |
|---------------|----------------------|
| Кто пользователь | Принадлежит ли ему профиль №25 |
| Какие у него роли | Принадлежит ли ему заказ №15 |
| | Может ли он изменять документ №42 |

**Поэтому после проверки JWT требуется дополнительная проверка доступа к объекту.**

---

## Object Authorization

Типичная схема проверки:

```
JWT
  │
  ▼
Authentication
  │
  ▼
Role / Permission Check
  │
  ▼
Object Authorization   ← BOLA ломается здесь
  │
  ▼
Business Logic
```

---

## Уязвимый код

```java
Profile profile = repository.findById(profileId);
return profile;
```

**Проблема:** отсутствует проверка владельца объекта.

---

## Безопасный вариант

```java
Profile profile = repository.findById(profileId);

if (!profile.ownerId.equals(currentUser.id)) {
    throw new ForbiddenException();
}
```

**Ещё лучше:**

```java
repository.findByIdAndOwnerId(profileId, currentUser.id);
```

---

## Где может передаваться Object ID

**Не имеет значения.** Идентификатор может находиться:

- в URL
- в query-параметре
- в теле запроса
- в заголовке
- в cookie

```http
PUT /api/profile/25
```

или

```json
{
  "profileId": 25
}
```

С точки зрения безопасности это **эквивалентно**.

### Главное правило

> Безопасность определяется не местом передачи идентификатора объекта, а наличием проверки **Object Authorization** на backend.

---

## Что искать во время Code Review

При анализе API задавать вопросы:

- Кто вызывает API?
- Кто является владельцем объекта?
- Проверяется ли владелец объекта?
- Можно ли изменить Object ID?
- Где выполняется Object Authorization?
- Можно ли получить доступ к чужим данным?

---

## Практические правила

| ✅ Делать | ❌ Не делать |
|-----------|-------------|
| Проверять Object Authorization на каждом endpoint | Думать, что JWT достаточно для защиты объекта |
| Использовать ID из JWT/session, не из запроса | Доверять Object ID из URL, тела, заголовков |
| Делать `findByIdAndOwnerId` вместо `findById` | Полагать, что «сложный» ID (UUID) защищает |
| Помнить: BOLA === IDOR в контексте API | Путать аутентификацию с авторизацией объекта |

---

## Ключевые мысли

1. **JWT подтверждает личность пользователя**, но не подтверждает его право работать с конкретным объектом
2. **Проверка роли не заменяет проверку владельца объекта**
3. **BOLA — это API-аналог IDOR**
4. Object ID можно передавать любым способом. Важна не форма передачи, а **серверная проверка прав доступа**
