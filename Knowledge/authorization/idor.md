# IDOR (Insecure Direct Object Reference)

> Разновидность Broken Access Control, при которой пользователь получает доступ к чужому объекту, изменяя его идентификатор в запросе.

---

## Что такое IDOR

**Типичный пример:**

```http
GET /api/orders/123
```

Злоумышленник изменяет запрос:

```http
GET /api/orders/124
```

Если сервер возвращает чужой заказ **без проверки прав доступа** — это IDOR.

---

## Почему возникает

**Главная причина:** сервер получает идентификатор объекта от клиента, но не проверяет, имеет ли пользователь право получить именно этот объект.

> [WARN] Проблема не в URL и не в формате идентификатора. Проблема — в отсутствии **Object Authorization**.

---

## Что такое Direct Object Reference

### Object

Объектом может быть:
- пользователь
- заказ
- документ
- файл
- комментарий
- счёт

### Reference

Способ обращения к объекту:

```
/users/15
/orders/42
/files/99
```

### Direct

Пользователь **напрямую управляет** идентификатором объекта.

---

## Root Cause

```
Сервер доверяет идентификатору, полученному от клиента.
```

**Правильный принцип:** никогда не доверять идентификаторам объектов, полученным от пользователя.

---

## Уязвимый код

```java
@GetMapping("/orders/{id}")
public Order getOrder(@PathVariable Long id) {
    return repository.findById(id);
}
```

**Проблема:** отсутствует проверка владельца объекта.

---

## Безопасный вариант

```java
Order order = repository.findById(id);

if (!order.getOwnerId().equals(currentUser.getId())) {
    throw new ForbiddenException();
}

return order;
```

**Ещё лучше:**

```java
repository.findByIdAndOwnerId(id, currentUser.getId());
```

Так объект, не принадлежащий пользователю, вообще не будет найден.

---

## Что искать во время Code Review

Если видишь:

```java
repository.findById(id)
// или
repository.findOne(id)
// или
repository.get(id)
```

сразу задавай вопросы:

- Кто передаёт `id`?
- Можно ли изменить `id`?
- Где проверяется владелец объекта?
- Где выполняется Object Authorization?
- Может ли обычный пользователь запросить чужой объект?

## Может ли SAST найти IDOR?

**Короткий ответ:** иногда может заподозрить, но редко может доказать.

### Почему?

SAST анализирует код. Он видит:

```
Request
    │
    ▼
Controller
    │
    ▼
findById(id)
    │
    ▼
Response
```

Но он **не знает**:
- кому принадлежит объект
- кто должен иметь к нему доступ
- какие правила действуют в данной системе
- какие существуют исключения

Это уже относится к **бизнес-логике** приложения.

### Почему SQL Injection найти проще?

Для SQL Injection существует универсальное правило:

```
User Input
    │
    ▼
SQL Query
```

Это **почти всегда опасно**.

Для IDOR такого универсального правила нет.

**Пример:** запрос `GET /repositories/15` в GitHub может быть абсолютно легальным запросом к публичному репозиторию. А в интернет-банке аналогичный запрос `GET /accounts/15` без проверки владельца уже является критической уязвимостью.

### Современные SAST

Современные инструменты (CodeQL, Semgrep, Fortify, Checkmarx и др.) способны находить **подозрительные места**, например:
- получение объекта по пользовательскому ID
- отсутствие вызова известного механизма авторизации
- подозрительный поток данных

Но они, как правило, не могут автоматически определить, является ли это реальной уязвимостью.

> Результат часто требует **ручной проверки AppSec-инженером**.

---

## Практические правила

| [OK] Делать | [NO] Не делать |
|-----------|-------------|
| Не доверять идентификаторам объектов от клиента | Использовать ID из URL без проверки |
| Проверять владельца объекта на backend | Полагаться на «сложный» формат ID (GUID, хэш) |
| Ограничивать выборку сразу (`findByIdAndOwnerId`) | Получать объект и проверять права постфактум |
| Помнить: проверка роли ≠ проверка доступа к объекту | Думать, что SAST найдёт все IDOR |

---

## Ключевые мысли

1. **IDOR — это проблема отсутствия проверки доступа к конкретному объекту**, а не проблема формата идентификатора
2. SAST хорошо ищет нарушения технических правил, но значительно хуже справляется с нарушениями **бизнес-логики**
3. Современные SAST могут обнаружить подозрительные участки кода, но решение о наличии IDOR чаще всего принимает **AppSec-инженер** после анализа логики приложения
