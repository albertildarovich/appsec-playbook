# A04 — Insecure Design

> **Суть:** Ошибки проектирования системы, а не ошибки реализации. Код может быть идеальным, но архитектура позволяет злоумышленнику добиться цели.
>
> **Ключевой вопрос:** «Что может пойти не так?» вместо «Как написать безопасный код?»

---

## Быстрый чек-лист

- [ ] Never Trust the Client — критические данные (цена, роль, статус) определяются сервером?
- [ ] Есть ли лимиты и rate limiting на критических операциях?
- [ ] Требуется ли MFA для опасных действий (крупные переводы, смена пароля)?
- [ ] Можно ли отменить / восстановить критическую операцию?
- [ ] Password Reset Token — короткоживущий, одноразовый, не множественный?
- [ ] Анализировали ли Abuse Cases (не только Use Cases)?
- [ ] Учтена ли Human Error (случайное удаление, лишний ноль)?

---

## Примеры Insecure Design

| Сценарий | Проблема | Решение |
|----------|----------|---------|
| Банковский перевод | Нет лимитов, нет MFA | Лимиты + MFA + задержка для новых получателей |
| Never Trust the Client | Клиент шлёт цену/роль | Только ID товара, сервер вычисляет |
| Password Reset | Бесконечный токен | 15 мин, одноразовый, инвалидация старых |
| SMS Bombing | Безлимитный запрос кода | Backoff + CAPTCHA + Cooldown |
| Удаление аккаунта | Мгновенное безвозвратное удаление | Grace period 30 дней + подтверждение |
