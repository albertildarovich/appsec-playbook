# Secure Design Principle — Least Privilege

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Least Privilege (Минимальные привилегии)** — принцип Secure Design, согласно которому каждый субъект (пользователь, процесс, сервис) должен иметь **минимально необходимый набор прав** для выполнения своих задач и **только на время** выполнения этих задач.

**Основная идея:**
Давать ровно столько прав, сколько нужно для работы, и ни на йоту больше.

---

## Зачем нужен Least Privilege?

- **Ограничение ущерба** — если учётная запись скомпрометирована, злоумышленник получает только минимум
- **Снижение случайных ошибок** — меньше прав = меньше вероятность случайно удалить/изменить важные данные
- **Упрощение аудита** — легче отследить, кто что сделал, когда прав мало
- **Принцип наименьшего удивления** — сервис не может сделать то, чего от него не ждут

---

## Least Privilege vs Broad Access

| | Least Privilege | Broad Access |
|---|---|---|
| **Подход** | Минимум прав для работы | Максимум прав "на всякий случай" |
| **Безопасность** | Высокая (ограниченный ущерб при компрометации) | Низкая (широкий простор для атаки) |
| **Управление** | Сложнее (нужно точно определить права) | Проще (один раз дал — забыл) |
| **Пример** | service-a имеет доступ только к своей таблице в БД | service-a имеет admin доступ ко всей БД |

## Примеры

### База данных

**Плохо:**
```sql
-- Приложение имеет полный доступ к БД
GRANT ALL PRIVILEGES ON database.* TO 'app_user'@'%';
```

**Хорошо:**
```sql
-- Только необходимые операции над конкретными таблицами
GRANT SELECT, INSERT, UPDATE ON database.orders TO 'app_user'@'app-server';
GRANT SELECT ON database.products TO 'app_user'@'app-server';
-- Нет DELETE, нет DROP, нет доступа к другим таблицам
```

### Kubernetes

**Плохо:**
```yaml
# Cluster-admin для сервисного аккаунта
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
subjects:
  - kind: ServiceAccount
    name: deployer
    namespace: default
roleRef:
  kind: ClusterRole
  name: cluster-admin  # [NO] Слишком широко
```

**Хорошо:**
```yaml
# Только необходимые права в конкретном namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: my-app
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "watch", "list"]  # [OK] Только чтение подов
```

### Процессы

**Плохо:**
```bash
# Процесс с root правами для простой задачи
sudo python server.py
```

**Хорошо:**
```bash
# Создаём пользователя с минимальными правами
useradd --system --no-create-home app-service
chown app-service:app-service /opt/app
su -s /bin/bash -c '/opt/app/server.py' app-service
```

### Права пользователей

**Плохо:**
```javascript
// Все пользователи — админы
user.role = 'admin';  // [NO]
```

**Хорошо:**
```javascript
// Минимальные права по умолчанию
user.role = 'viewer';  // [OK]
// Повышение прав — явное действие с approval
```

## Архитектурное мышление

Least Privilege — это баланс между безопасностью и operational overhead.

**Правильный вопрос:**
> «Какое минимальное количество прав необходимо этому субъекту для выполнения его функции?»

**Trade-offs:**
- **Безопасность vs Управляемость** — слишком детальные права сложно администрировать (role explosion)
- **Безопасность vs Производительность** — каждая проверка прав требует времени
- **Принцип vs Практика** — в идеале права должны быть временными и динамическими, но это сложно

---

## Security Architect Perspective

> На практике Least Privilege — это постоянная борьба с «а дай-ка я дам admin, чтобы не думать». Самая частая ошибка — дать широкие права «сейчас», а «потом сузить». «Потом» не наступает никогда. Хороший архитектор начинает с минимально возможных прав и расширяет только при доказанной необходимости. Каждое расширение должно быть зафиксировано в ADR с обоснованием: почему без этого нельзя, какие риски мы принимаем и когда можно будет откатить. Отдельная боль — сервис-сервисное взаимодействие в микросервисах, где каждому сервису нужны права на чтение/запись определённых данных. Здесь помогает политика «каждый сервис имеет доступ только к своим таблицам/topics/queue», а кросс-сервисный доступ — только через API с собственной авторизацией.

---

## Связь с другими принципами

- **Defense in Depth** — Least Privilege ограничивает ущерб, если один слой защиты обойдён
- **Fail Secure** — при ошибке проверки прав — отказ, а не расширение
- **Reduce Attack Surface** — меньше прав = меньше возможностей для атаки
- **Separation of Privilege** — разделение критичных операций на несколько условий
- **Secure Defaults** — по умолчанию минимальные права

## Common Interview Mistakes

### [NO] Категоричный ответ
> «Нужно дать минимум прав, даже если это замедлит разработку. Безопасность важнее.»

**Почему это проблема:** Это утопия. Если процесс получения прав занимает 2 недели, разработчики начнут использовать admin-аккаунты «чтобы не ждать». Least Privilege должен быть сбалансирован с operational efficiency.

**Зрелая формулировка:**
> «Least Privilege — это не про "дать минимум любой ценой". Это про осознанное управление правами. Быстрые и временные права (на 24 часа) лучше, чем постоянные широкие права. Главное — чтобы повышение прав было временным, аудитируемым и автоматически отзывалось.»

### [NO] Категоричный ответ
> «Root в контейнере — это нормально, контейнеры же изолированы.»

**Почему это проблема:** Контейнеры не изолированы на 100%. Escape из контейнера даёт злоумышленнику root на хосте. Даже без escape — процессы от root в контейнере могут делать больше, чем нужно.

**Зрелая формулировка:**
> «Контейнеры не добавляют магической изоляции. Они используют общее ядро с хостом. Root в контейнере — это root на хосте при любой уязвимости в рантайме. Все контейнеры должны запускаться с non-root пользователем и read-only root filesystem, если это возможно.»

### [NO] Категоричный ответ
> «JWT claims достаточно для авторизации — зачем ещё отдельные проверки?»

**Почему это проблема:** JWT claims статичны на время жизни токена. Если права отозвали, JWT продолжит работать до expiry.

**Зрелая формулировка:**
> «JWT claims — это удобно для базовой авторизации (роль, scope), но не заменяет проверки на каждый запрос. Если права чувствительны или могут часто меняться — нужен Policy Engine (OPA), который проверяет актуальные политики на каждый запрос, а не доверяет claims в токене.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Что такое Least Privilege?** | Принцип, согласно которому каждый субъект получает минимально необходимый набор прав для выполнения своих задач. |
| **Почему нельзя давать все права «на всякий случай»?** | Это увеличивает ущерб при компрометации учётной записи и усложняет аудит. |
| **Как применять Least Privilege в Kubernetes?** | Использовать RBAC вместо cluster-admin, ограничивать ServiceAccount правами только на свой namespace, запрещать privileged containers. |
| **Что такое role explosion и как с ним бороться?** | Когда ролей становится слишком много из-за детального разграничения. Решение: ABAC, policy-as-code (OPA), groups-based management. |
| **Как сбалансировать Least Privilege и скорость разработки?** | Временные elevated права (с TTL) + self-service portal + audit log. Разработчик получает права быстро, но временно и с записью. |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Процессы от root / Administrator | Любая уязвимость = полный контроль |
| Одна учётная запись БД для всего приложения | SQL Injection = доступ ко всем данным |
| Все пользователи — admin | Нет разграничения, любой может всё |
| Сервис-аккаунты с cluster-admin | Компрометация одного сервиса = весь кластер |
| Права не отзываются при смене роли | Бывший сотрудник/админ сохраняет доступ |

---

## Lessons Learned

- Начинай с минимальных прав и расширяй при необходимости (не наоборот)
- Права должны быть **временными** где возможно (JIT — Just-In-Time access)
- Каждое расширение прав — событие для audit log
- Ревью прав должно быть регулярным (квартальный review)
- В микросервисах каждый сервис имеет доступ только к своим данным
- JIT access + audit = баланс безопасности и скорости разработки
