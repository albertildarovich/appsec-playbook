# Secure Design Principle — Reduce Attack Surface

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Reduce Attack Surface** — принцип Secure Design, согласно которому необходимо **минимизировать** количество компонентов, интерфейсов, функций и точек входа, доступных потенциальному атакующему.

**Основная идея:**
Лучший способ защитить функциональность — не создавать её без необходимости.

---

## Зачем нужен этот принцип?

Каждый новый компонент увеличивает:
- **вероятность** появления уязвимости;
- **стоимость** сопровождения;
- **сложность** Threat Modeling;
- **количество** сценариев атаки.

**Главная идея:**
> Перед добавлением новой функции стоит спросить: «А действительно ли она нужна?»
>
> Иногда лучший способ защиты — удалить ненужную функциональность.

---

## Reduce Attack Surface vs Feature Rich

| | Reduce Attack Surface | Feature Rich |
|---|---|---|
| **Подход** | Минимум функций, каждая оправдана | Максимум возможностей |
| **Безопасность** | Выше (меньше кода для атаки) | Ниже (больше кода, больше ошибок) |
| **Сложность** | Ниже | Выше |
| **User Experience** | Может быть ограничен | Богатый функционал |
| **Пример** | API только с нужными endpoint'ами | API со всеми debug/test endpoint'ами |

## Примеры

### API

**Плохо (большая поверхность):**
```
POST /api/debug
POST /api/internal
POST /api/legacy
POST /api/test
GET  /api/users (возвращает всех)
```

**Хорошо (минимизировано):**
```
POST /api/orders
POST /api/payments
GET  /api/orders/{id}
```
Оставлены только публичные бизнес-методы. Каждый endpoint оправдан.

### Docker

**Плохо:**
```dockerfile
FROM ubuntu:latest
RUN apt-get install curl wget ssh vim netcat
```

**Хорошо (минимальный image):**
```dockerfile
FROM alpine:latest
# Только то, что нужно для работы приложения
RUN apk add --no-cache ca-certificates
COPY ./app /app
CMD ["/app"]
```

Не устанавливать `curl`, `wget`, `ssh`, `vim`, если контейнеру они не нужны.

### Kubernetes

**Избегать:**
- лишние Ingress (открывают доступ извне)
- Service типа LoadBalancer без необходимости
- открытые NodePort
- лишние ClusterRole с широкими правами

### Backend

**Удалить из Production:**
- Debug Endpoints (`/debug`, `/health/detailed`)
- Test API (`/api/test`, `/api/mock`)
- Legacy Controllers (неиспользуемый код)
- Admin панели без сетевых ограничений

### Error Handling

**Плохо (избыточная информация):**
```json
{
    "error": "File not found",
    "stackTrace": "at FileService.get(/app/src/services/file.js:42)",
    "internalId": "ERR-42",
    "dbQuery": "SELECT * FROM files WHERE id = 123"
}
```

**Хорошо (минимум информации):**
```json
{
    "error": "Resource not found"
}
```

## Архитектурное мышление

Reduce Attack Surface — это постоянный компромисс между функциональностью и безопасностью.

**Правильный вопрос:**
> Каждую новую функцию спрашиваем: «Какую бизнес-ценность она даёт?» и «Какую поверхность атаки открывает?»

**Trade-offs:**
- **Функциональность vs Безопасность** — удаление функции может снизить usability
- **Convenience vs Security** — debug endpoint удобен для разработки, но опасен в production
- **Time-to-market vs Attack Surface** — быстрые релизы часто добавляют лишние функции

---

## Security Architect Perspective

> В реальных проектах самый сложный разговор — это «Почему мы не можем оставить этот endpoint для отладки?» Reduce Attack Surface — это принцип, который идёт вразрез с культурой «добавь побольше, потом уберём». Хороший архитектор понимает, что код, попавший в production, редко удаляется. Поэтому он настаивает на том, чтобы каждое публичное API, каждый открытый порт, каждый endpoint были осознанным решением, а не результатом «чтобы было». Лучшая практика: всё, что не нужно в production, должно быть либо за флагом, либо за VPN, либо — удалено.

---

## Связь с другими принципами

- **Least Privilege** — ограничивает права, Reduce Attack Surface ограничивает функции
- **Economy of Mechanism** — уменьшает сложность, что снижает количество ошибок
- **Open Design** — безопасность не должна зависеть от скрытия функциональности (security through obscurity)
- **Secure Defaults** — новые функции по умолчанию отключены

## Common Interview Mistakes

### [NO] Категоричный ответ
> «Нужно просто закрыть все порты, кроме 80 и 443, и проблема решена.»

**Почему это проблема:** Attack Surface — это не только порты. Это API, UI, обработчики файлов, ошибки, логи, зависимости. Можно закрыть все порты, но оставить Debug Mode в API.

**Зрелая формулировка:**
> «Attack Surface — это всё, с чем взаимодействует пользователь или злоумышленник: endpoint'ы, формы, поля ввода, обработчики файлов, error messages, headers — и даже метаданные. Сокращение поверхности — это не про фаерволы, а про осознанное проектирование каждой точки входа в систему.»

### [NO] Категоричный ответ
> «Нельзя удалять API — оно может понадобиться в будущем. Лучше оставить, но не документировать.»

**Почему это проблема:** Security through obscurity не работает. Злоумышленники найдут недокументированное API через fuzzing или анализируя frontend.

**Зрелая формулировка:**
> «Если API не нужно сейчас — его нужно удалить или отключить (feature flag). Недокументированное API — это не защита, а бомба замедленного действия. Его найдут раньше, чем вы успеете его защитить. Если очень нужно оставить — только за флагом, с аутентификацией, аудитом и планом удаления.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Что такое Attack Surface?** | Совокупность всех точек входа, функций и интерфейсов системы, доступных потенциальному атакующему. |
| **Как уменьшить поверхность атаки?** | Удалить ненужные функции, закрыть неиспользуемые порты, отключить debug режим, минимизировать зависимости, использовать allowlist вместо blocklist. |
| **Почему удаление API безопаснее его защиты?** | Удалённый endpoint нельзя взломать. Защищённый — можно (ошибка конфигурации, уязвимость, человеческий фактор). |
| **Какие элементы Kubernetes увеличивают Attack Surface?** | Лишние Ingress, LoadBalancer Services, NodePort, широкие ClusterRole, hostNetwork, privileged containers. |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Старые API endpoints остаются навсегда | Никто не знает, какие данные они отдают |
| Debug-функции попадают в Production | Info disclosure, RCE |
| Неиспользуемые сервисы продолжают работать | Забытые уязвимости |
| Открытые административные панели | Доступ без аутентификации |
| Избыточные зависимости (npm, pip) | Линковка уязвимостей в неиспользуемом коде |

---

## Lessons Learned

- Любая функция — потенциальная точка атаки
- Минимизация функциональности уменьшает риск
- Самый безопасный код — код, которого нет
- Security through obscurity (недокументированное API) — не защита
- Feature flag лучше, чем удаление (можно быстро вернуть), но флаги тоже нужно чистить
- Каждый endpoint, каждая зависимость, каждый открытый порт должны быть осознанным решением
