# Secure Design Principle — Economy of Mechanism

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Economy of Mechanism (Экономия механизма)** — принцип Secure Design, согласно которому механизмы безопасности должны быть **максимально простыми** и небольшими по объёму.

**Основная идея:**
Чем проще система, тем легче убедиться, что она безопасна.

---

## Зачем нужен этот принцип?

Любая дополнительная сложность увеличивает:
- **вероятность появления ошибок** — больше кода = больше багов;
- **стоимость сопровождения** — сложные системы дороже поддерживать;
- **вероятность неправильной настройки** — чем больше опций, тем выше шанс ошибки;
- **сложность аудита** — в сложной системе трудно отследить, что произошло;
- **сложность Threat Modeling** — больше компонентов = больше связей = больше угроз.

**Главная идея:**
> Сложные системы не обязательно менее безопасны, но их **значительно сложнее** сделать безопасными.

---

## Простота vs Сложность

| | Простота (Economy of Mechanism) | Избыточная сложность |
|---|---|---|
| **Подход** | Минимум компонентов, каждый оправдан | Много уровней, правил, исключений |
| **Тестирование** | Легко покрыть все сценарии | Невозможно протестировать все комбинации |
| **Code Review** | Быстрый, понятный | Долгий, easy to miss |
| **Threat Modeling** | За час можно смоделировать полностью | Неделя и всё равно будут пропуски |
| **Ошибки** | Минимум мест для ошибки | Каждый компонент — потенциальный баг |

---

## Почему это важно?

Представим две реализации авторизации.

**Вариант 1 (простой):**
```
JWT → RBAC → Policy Engine
```
Три понятных уровня. Легко понять, почему пользователь получил или не получил доступ.

**Вариант 2 (сложный):**
```
JWT → RBAC → ABAC → Custom Rules → Feature Flags → Dynamic Config → Legacy Permission Service
```
Теперь, чтобы понять, почему пользователь получил доступ, нужно проанализировать **множество компонентов**. Такую систему гораздо сложнее:
- тестировать;
- сопровождать;
- проводить Code Review;
- моделировать угрозы.

## Примеры

### Authentication

**Плохо (самописный протокол):**
```python
# Собственный протокол авторизации — 500 строк
# Ошибки в реализации, нет аудита, сложно тестировать
def verify_auth(token, timestamp, nonce, signature):
    # своя криптография, свои проверки
    pass
```

**Хорошо (использовать стандарт):**
```python
# OAuth 2.0 через проверенную библиотеку
from authlib.integrations.flask_client import OAuth
oauth.register('provider')
```

Использовать проверенный OAuth 2.0 вместо собственного протокола авторизации.

### Криптография

**Плохо:**
```python
# Самописное шифрование
def encrypt(data):
    result = []
    for byte in data:
        result.append(byte ^ 0x42)  # 😱
    return bytes(result)
```

**Хорошо:**
```python
# Использовать стандартные алгоритмы
from cryptography.fernet import Fernet
cipher = Fernet(key)
encrypted = cipher.encrypt(data)
```

Использовать AES, RSA, Ed25519 через проверенные библиотеки. Никогда не писать свою криптографию.

### CI/CD

**Плохо (дублирование):**
```
service-a/security.sh
service-b/security.sh
service-c/security.sh  # все 3 делают одно и то же по-разному
```

**Хорошо (централизованный pipeline):**
```
security-pipeline/  # один источник правды
  ├── lint.sh
  ├── scan.sh
  └── deploy.sh
```

Один централизованный Security Pipeline проще и безопаснее, чем множество различных скриптов с одинаковой логикой.

### Kubernetes

**Плохо:**
Собственная система управления правами поверх Kubernetes.

**Хорошо:**
Использовать встроенный **RBAC** + **Admission Controller** для политик. Не изобретать велосипед.

## Архитектурное мышление

Economy of Mechanism — это не про "удалить всё лишнее", а про **осознанную простоту**.

**Правильный вопрос:**
> «Какую проблему решает каждый из этих компонентов? Можно ли решить её проще?»

**Trade-offs:**
- **Простота vs Гибкость** — простые системы сложнее расширять
- **Standard vs Custom** — стандартные решения безопаснее, но могут не покрывать всех требований
- **Простота vs Функциональность** — иногда сложность оправдана бизнес-требованиями

---

## Security Architect Perspective

> Этот принцип чаще всего нарушают, когда в архитектуру добавляют «ещё один слой на всякий случай». Каждый новый компонент кажется безобидным сам по себе, но в совокупности они создают систему, где никто не понимает, как на самом деле работает авторизация. Самый опасный паттерн — наслоение: когда новый механизм добавляется поверх старого, потому что «страшно удалять legacy». Economy of Mechanism требует discipline: каждый компонент должен иметь чёткое обоснование, а если компонент перестал быть нужен — его удаляют, а не оставляют «для истории». Хороший архитектор регулярно проводит «spring cleaning» архитектуры: какие компоненты можно объединить, какие удалить, какие заменить более простыми.

---

## Economy of Mechanism ≠ Минимум функций

Иногда этот принцип понимают неправильно.

**Он не означает:**
> «Удалим половину возможностей.»

**Он означает:**
> «Решим задачу максимально простым способом.»

**Плохо:**
Пять разных способов аутентификации без необходимости.

**Хорошо:**
Один понятный механизм аутентификации, который покрывает все требования.

---

## Связь с другими принципами

- **Reduce Attack Surface** — меньше компонентов = меньше точек атаки
- **Open Design** — простые механизмы легче анализировать и проверять
- **Defense in Depth** — уровни защиты должны быть независимыми, но не излишне сложными
- **Complete Mediation** — простую систему легче заставить проверять каждый запрос

## Common Interview Mistakes

### ❌ Категоричный ответ
> «Всегда нужно использовать самый простой вариант. Сложность — враг безопасности.»

**Почему это проблема:** Бывают ситуации, когда сложность оправдана. Например, микросервисная архитектура сложнее монолита, но может быть необходима для масштабирования. Задача AppSec — не бороться со сложностью любой ценой, а не добавлять лишнюю.

**Зрелая формулировка:**
> «Economy of Mechanism — это борьба с **неоправданной** сложностью, а не с любой сложностью. Если сложность оправдана бизнес-требованиями (масштабирование, compliance, regulatory), задача AppSec — сделать её управляемой: документировать, тестировать, моделировать угрозы. Но если компонент можно убрать без потери функциональности — его нужно убрать.»

### ❌ Категоричный ответ
> «Нужно всегда писать свою реализацию, потому что мы лучше знаем свой контекст.»

**Почему это проблема:** Своя реализация криптографии, авторизации, аутентификации — это практически гарантированные ошибки. Стандартные библиотеки прошли тысячи часов аудита и тестирования. Ваш код — нет.

**Зрелая формулировка:**
> «Стандартные механизмы почти всегда предпочтительнее самописных, потому что они аудированы, протестированы и документированы. Исключение — когда стандартное решение не покрывает специфические требования (например, custom compliance rules). Но даже в этом случае стоит максимально использовать готовые компоненты и добавлять только то, чего действительно не хватает.»

### ❌ Категоричный ответ
> «Нам нужно 5 разных способов аутентификации: пароль, OAuth, SMS, биометрия, API key — каждый сервис выбирает сам.»

**Почему это проблема:** Пять механизмов = пять поверхностей для атаки, пять code paths для тестирования, пять способов ошибиться. При этом 80% пользователей используют один-два способа.

**Зрелая формулировка:**
> «Лучше иметь один-два хорошо проработанных механизма аутентификации, чем пять «на всякий случай». Каждый дополнительный механизм должен быть обоснован реальной потребностью пользователей, а не «чтобы было». Если нужно несколько — они должны быть реализованы через единый абстракционный слой (например, Strategy pattern), а не размазаны по коду.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Почему простая система безопаснее сложной?** | Потому что в простой системе меньше мест для ошибки, её легче тестировать, аудировать и моделировать угрозы. |
| **Когда сложность оправдана?** | Когда она продиктована бизнес-требованиями: масштабирование, compliance, regulatory. Но каждый элемент сложности должен быть осознанным решением. |
| **Почему не стоит писать собственную криптографию?** | Криптография требует глубокой экспертизы. Стандартные алгоритмы (AES, RSA, Ed25519) прошли тысячи часов аудита. Ваша реализация — нет. |
| **Как связаны сложность архитектуры и количество ошибок?** | Прямая зависимость: больше компонентов = больше связей = больше мест для ошибки = сложнее тестировать = выше вероятность пропустить уязвимость. |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Самописные механизмы безопасности без необходимости | Непротестированный код с гарантированными ошибками |
| Несколько пересекающихся систем авторизации | Невозможно понять, какая система что решает |
| Чрезмерно сложные политики доступа | Администраторы ошибаются в настройке |
| Дублирование логики безопасности в разных сервисах | Обновление нужно делать в N местах |

---

## Lessons Learned

- Простые решения легче проверять и сопровождать
- Каждый новый компонент увеличивает вероятность ошибок
- Использование стандартных механизмов часто безопаснее разработки собственных
- Economy of Mechanism — это борьба с **неоправданной** сложностью, а не с любой сложностью
- Senior AppSec не говорит «это слишком сложно». Он говорит: «Какую проблему решает каждый из этих компонентов?»
