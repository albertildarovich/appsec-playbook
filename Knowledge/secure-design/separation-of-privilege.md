# Secure Design Principle — Separation of Privilege

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Separation of Privilege (Разделение привилегий)** — принцип Secure Design, согласно которому выполнение критически важных операций должно требовать **нескольких независимых условий или факторов**, а не одного.

**Основная идея:**
Одного условия не должно быть достаточно для выполнения чувствительной операции.

### Что считается «независимыми условиями»?

Это не обязательно два разных пароля. Независимыми могут быть:
- **разные факторы аутентификации** — password + TOTP (MFA)
- **разные пользователи** — инициатор + утверждающий (dual approval)
- **разные роли** — разработчик + tech lead + security
- **разные сервисы** — API Gateway + Auth Service + Policy Engine
- **разные механизмы проверки** — код + SAST + review

---

## Зачем нужен Separation of Privilege?

Некоторые операции настолько опасны, что доверять их одному человеку или одному механизму — слишком рискованно:

- удалить production database;
- подтвердить платёж на $1M;
- выпустить сертификат;
- повысить права до admin;
- одобрить код в production.

**Если одно условие (пароль, токен, сессия) может выполнить операцию — это single point of failure для безопасности.**

**Главная идея:**
> Разделение привилегий гарантирует, что для опасной операции нужно несколько независимых согласий.

---

## Separation of Privilege vs Least Privilege

Это **самая частая путаница** на интервью. Принципы про разное:

| | Least Privilege | Separation of Privilege |
|---|---|---|
| **Вопрос** | «Сколько прав дать?» | «Сколько условий нужно для опасной операции?» |
| **Ответ** | Минимум прав для работы | Несколько независимых условий |
| **Пример** | Оператор БД может только SELECT/INSERT | Чтобы удалить таблицу, нужно approval от двух администраторов |
| **Нарушение** | Слишком широкие права | Один человек может выполнить опасную операцию в одиночку |

**Ключевое отличие:**
- **Least Privilege** — про **объём** прав
- **Separation of Privilege** — про **количество независимых условий** для опасного действия

## Примеры

### Финансовые операции

**Плохо (нарушение):**
```javascript
// Один сотрудник может перевести $1M
app.post('/api/transfer', (req, res) => {
    const user = authenticate(req);
    if (user.role === 'finance') {
        transfer(req.body.amount, req.body.to);
    }
});
```

**Хорошо (Separation of Privilege):**
```javascript
// Нужно два независимых подтверждения
app.post('/api/transfer', (req, res) => {
    const user = authenticate(req);
    if (user.role === 'finance' && req.body.approvedBy) {
        // Проверяем, что approvedBy — другой сотрудник
        const approver = getUser(req.body.approvedBy);
        if (approver.role === 'finance-manager' && approver.id !== user.id) {
            transfer(req.body.amount, req.body.to);
        }
    }
});
```

**Реальный кейс:** В банковских системах перевод > $10k требует двух подписей.

### Kubernetes

**Плохо (один человек может всё):**
```yaml
# cluster-admin — полный контроль
roleRef:
  name: cluster-admin
```

**Хорошо (разделение ролей):**
```yaml
# Один управляет подами, другой — секретами
---
kind: Role
name: pod-manager
rules:
  - resources: ["pods"]
    verbs: ["create", "delete"]
---
kind: Role
name: secret-manager  
rules:
  - resources: ["secrets"]
    verbs: ["create", "delete"]
# Никто не может и создавать поды, и читать секреты
```

### Code Review

**Плохо:**
```python
# Разработчик может смержить свой же код
git push origin main  # 
```

**Хорошо:**
```python
# Нужен approval от другого разработчика
# PR → Code Review → Approval → Merge
# Никто не может смержить свой код без ревью
```

**Реальный кейс:** branch protection в GitHub + required reviewers.

### Production Access

**Плохо:**
```
Один admin имеет доступ к production через VPN + sudo
```

**Хорошо (Break Glass — экстренный доступ с контролем):**
```
Запрос доступа → Approval от второго admin → Временный доступ (TTL) → Audit log
Или: два admin должны одновременно ввести свои ключи
```

### MFA как Separation of Privilege

MFA — это классическая реализация Separation of Privilege:
- **Фактор 1:** что ты знаешь (пароль)
- **Фактор 2:** что ты имеешь (токен/телефон)
- **Фактор 3:** кто ты (биометрия)

Компрометация пароля (фишинг) не даёт доступ без второго фактора.

## Архитектурное мышление

Separation of Privilege — это баланс между безопасностью и operational efficiency.

**Правильный вопрос:**
> «Какие операции настолько опасны, что доверять их одному субъекту/условию — неприемлемый риск?»

**Trade-offs:**
- **Безопасность vs Скорость** — двухфакторное подтверждение замедляет операции
- **Безопасность vs Удобство** — чем больше условий, тем менее удобна система
- **Granularity vs Complexity** — слишком детальное разделение парализует работу

---

## Security Architect Perspective

> Самая частая ошибка — не разделять привилегии вообще. Вторая по частоте — разделить их неправильно, так что одно и то же лицо контролирует оба условия. Например, admin, который и выдаёт доступ, и audитирует его использование — это mock separation. Реальное разделение требует, чтобы условия были независимыми не только технически, но и организационно: разные люди, разные системы, разные каналы. Хороший архитектор для каждой опасной операции спрашивает: «Кто может подтвердить, что это действие легитимно?» и «Может ли человек, выполняющий операцию, также выполнить и подтверждение?» Если да — это не separation.

### Важный нюанс: Risk-based approach

На практике Separation of Privilege — это управление рисками, а не догма.

| Операция | Достаточно одного условия | Нужен Separation of Privilege |
|----------|--------------------------|-------------------------------|
| Изменить аватар | [OK] пароль | [NO] |
| Изменить email | [NO] | [OK] повторный ввод пароля или MFA |
| Перевести $10 | [OK] пароль | [NO] |
| Закрыть банковский счёт | [NO] | [OK] dual approval |
| Посмотреть свой профиль | [OK] аутентификация | [NO] |
| Удалить production namespace | [NO] | [OK] approval + second person |

Мы не применяем Separation of Privilege ко всему подряд. Мы применяем его там, где **последствия ошибки или компрометации достаточно серьёзны**, чтобы оправдать дополнительные проверки.

## Separation of Privilege на собеседовании

Этот принцип часто проверяют в вопросах про **архитектуру безопасных систем**.

### Пример: «Спроектируйте безопасный пайплайн деплоя»

**Junior** скажет: «Нужно, чтобы код прошёл тесты и SAST.»

**Senior** добавит:
- **Separation of Privilege:** разработчик не может смержить свой код без approval; тот, кто approval'ит, не может деплоить; тот, кто деплоит, не имеет доступа к production secrets
- **Least Privilege:** CI/CD pipeline имеет доступ только к нужным сервисам
- **Complete Mediation:** каждый этап пайплайна проверяет права независимо

---

## Связь с другими принципами

- **Least Privilege** — про объём прав, Separation of Privilege — про количество условий
- **Defense in Depth** — несколько слоёв защиты; Separation of Privilege — несколько условий для одного действия
- **Fail Secure** — при ошибке одного условия — отказ всей операции
- **Psychological Acceptability** — дополнительные проверки должны быть оправданными и не превращаться в бессмысленные препятствия

## Common Interview Mistakes

### [NO] Категоричный ответ
> «Separation of Privilege и Least Privilege — это одно и то же. Просто минимальные права.»

**Почему это проблема:** Это два разных принципа. Least Privilege — сколько прав. Separation of Privilege — сколько независимых условий нужно для опасной операции. Можно дать минимальные права (Least Privilege), но при этом один человек всё равно сможет выполнить критическую операцию.

**Зрелая формулировка:**
> «Least Privilege — про объём прав: дать ровно столько, сколько нужно. Separation of Privilege — про распределение контроля: опасная операция требует нескольких независимых согласий. Например, разработчику нужен доступ к CI/CD (Least Privilege — только к его сервисам), но он не может смержить свой PR без code review (Separation of Privilege).»

### [NO] Категоричный ответ
> «Двухфакторная аутентификация (MFA) — это не Separation of Privilege, это просто дополнительная защита.»

**Почему это проблема:** MFA — классический пример Separation of Privilege. Пароль (что знаешь) + токен (что имеешь). Компрометация одного фактора не даёт доступ.

**Зрелая формулировка:**
> «MFA — это реализация Separation of Privilege на уровне аутентификации. Система требует два независимых условия: знание (пароль) и обладание (токен). Аналогично в финансовых системах: операция требует two-person approval — это Separation of Privilege на уровне авторизации.»

### [NO] Категоричный ответ
> «Мы используем RBAC, поэтому Separation of Privilege у нас настроен.»

**Почему это проблема:** RBAC контролирует, кто что может делать. Но он не гарантирует, что для опасной операции нужно несколько независимых условий.

**Зрелая формулировка:**
> «RBAC решает задачу Least Privilege (кто какие роли имеет), но не Separation of Privilege. Для Separation of Privilege нужна дополнительная логика: операция требует approval от другой роли, или двухфакторное подтверждение, или временные ограничения. RBAC + Separation of Privilege — вместе, а не вместо.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Чем Separation of Privilege отличается от Least Privilege?** | Least Privilege — сколько прав дать. Separation of Privilege — сколько независимых условий нужно для опасной операции. |
| **Приведите пример Separation of Privilege в финансах.** | Перевод > $10k требует двух подписей: один сотрудник создаёт платёж, второй подтверждает. |
| **Как Separation of Privilege применяется в DevOps?** | Branch protection: разработчик не может смержить свой PR без review. Разделение: deployer не имеет доступа к production secrets напрямую. |
| **Что такое dual control?** | Режим, при котором критическая операция требует одновременного участия двух уполномоченных лиц. Например, два admin'а вводят свои ключи для расшифровки master key. |
| **Как Separation of Privilege связан с MFA?** | MFA — реализация Separation of Privilege: пароль (знание) + токен (обладание). Компрометация одного фактора недостаточна для доступа. |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Один admin может удалить production БД | Single point of failure для безопасности |
| Разработчик может смержить свой PR без review | Код с ошибками попадает в production |
| Admin и auditor — одно лицо | Аудит фиктивен |
| CI/CD pipeline имеет полный доступ ко всем сервисам | Компрометация pipeline = компрометация всего |
| Одна система выдаёт и проверяет сертификаты | Кто контролирует контролёра? |

---

## Lessons Learned

- **Separation of Privilege ≠ Least Privilege.** Одно про объём прав, другое про количество условий
- Критические операции не должны зависеть от одного механизма защиты
- Компрометация одного секрета не должна автоматически означать компрометацию всей операции
- Условия должны быть независимыми не только технически, но и организационно
- MFA, dual control, two-person approval, code review — всё это реализации Separation of Privilege
- Применяем принцип там, где последствия ошибки серьёзны, а не ко всему подряд
- Хороший вопрос для каждой операции: «Может ли один человек выполнить её без контроля?»
