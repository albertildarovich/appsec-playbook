# Secure Design Principle — Never Trust the Client

> **⚠️ Важно:** Это не классический принцип Saltzer & Schroeder, а современный принцип Secure Design, Secure Coding и Zero Trust, который используется практически во всех современных AppSec-практиках.

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Never Trust the Client (Никогда не доверяй клиенту)** — сервер никогда не должен доверять данным, логике или решениям, пришедшим от клиента.

**Основная идея:**
Клиент находится под полным контролем пользователя или атакующего.

---

## Зачем нужен Never Trust the Client?

Представим обычный интернет-магазин. Клиент отправляет запрос:

```json
{
    "product": 15,
    "price": 100,
    "role": "admin",
    "discount": 90
}
```

Можно ли доверять этим данным? **Нет.** Потому что пользователь сам их сформировал.

### Самая главная мысль

Для сервера не существует «честного клиента». Есть только **HTTP-запрос**.

Не важно:
- браузер;
- мобильное приложение;
- React / Flutter / iOS / Android.

Все они могут быть:
- изменены;
- перехвачены;
- переписаны;
- сгенерированы вручную.

Клиент — это **небезопасная среда**:
- браузером управляет пользователь (DevTools, расширения);
- мобильное приложение можно декомпилировать;
- HTTP-запросы можно перехватить и изменить (Burp Suite, mitmproxy);
- JavaScript код можно модифицировать.

**Сервер — единственное место, где можно доверять логике безопасности.**

### Почему нельзя доверять клиенту?

Потому что пользователь может использовать:
- Burp Suite;
- curl;
- Postman;
- собственный Python скрипт;
- собственный браузер;
- модифицированное мобильное приложение (Frida, декомпиляция APK).

И сервер не сможет отличить их от «настоящего» клиента, если будет доверять только интерфейсу.

**Главная идея:**
> Любая проверка на клиенте — это UX, а не Security. Настоящая защита всегда на сервере.

---

## Где нарушается этот принцип?

| Нарушение | Пример | Почему опасно |
|-----------|--------|---------------|
| Проверка прав только на UI | Скрыть кнопку «Удалить» для не-admin | Пользователь может отправить DELETE запрос через DevTools |
| Валидация только на фронтенде | Проверка формата email в JS | Пользователь может отправить любой payload через curl |
| Цена/скидка приходит с клиента | `{ "price": 0, "coupon": "HACK" }` | Пользователь может изменить цену в запросе |
| Роль/ID пользователя из запроса | `{ "role": "admin" }` | Пользователь может подставить любую роль |
| Секреты в клиентском коде | API ключ в JavaScript | Любой может прочитать и использовать |

## Примеры

### Это касается не только Web

Очень многие думают: «Это проблема JavaScript». Нет. Это проблема **любой клиентской логики**.

| Платформа | Инструмент атакующего |
|-----------|----------------------|
| **Web (React, Angular, Vue)** | DevTools, curl, Burp Suite |
| **Android** | Декомпиляция APK, Frida |
| **iOS** | Frida, объект-инъекция |
| **Desktop (Electron, .NET)** | Изменение бинарника, dnSpy |
| **GraphQL** | Сформировать собственный Query |
| **REST API** | Вызвать любой Endpoint |

### Реальный пример: Игровой сервер

**Плохо (доверяет клиенту):**
```javascript
// Клиент отправляет свой баланс
app.post('/api/game/add-coins', (req, res) => {
    // ❌ пользователь может отправить { "coins": 1000000 }
    user.coins += req.body.coins;
    user.save();
});
```

**Хорошо (сервер сам рассчитывает):**
```javascript
// Сервер хранит баланс и сам рассчитывает изменения
app.post('/api/game/complete-level', (req, res) => {
    const level = req.body.level;
    const reward = getLevelReward(level); // сервер определяет награду
    user.coins += reward;                  // сервер рассчитывает баланс
    user.save();
});
```

### Проверка прав

**Плохо (только на клиенте):**
```tsx
// UI скрывает кнопку, но API не защищён
function DeleteButton({ user, orderId }) {
    if (user.role !== 'admin') return null;  // ❌ только UX

    return <button onClick={() => deleteOrder(orderId)}>Delete</button>;
}
```

**Хорошо (сервер проверяет):**
```python
@app.delete('/api/orders/{order_id}')
def delete_order(order_id):
    current_user = get_current_user()
    # Сервер сам проверяет права
    if not current_user.has_permission('order:delete'):
        return 403
    # Сервер проверяет ownership
    order = Order.find(order_id)
    if order.owner_id != current_user.id and not current_user.is_admin:
        return 403
    order.delete()
```

### Валидация

**Плохо (только на клиенте):**
```javascript
// Frontend validation
function validateEmail(email) {
    return email.includes('@');  // ❌ легко обойти
}
```

**Хорошо (сервер валидирует):**
```python
@app.post('/api/users')
def create_user():
    data = request.json
    if not validate_email(data['email']):  # ✅ серверная валидация
        return 400
    if not validate_sql(data['name']):     # ✅ защита от injection
        return 400
    user = create_user(data)
    return user
```

### Цена товара

**Плохо (клиент передаёт цену):**
```json
// POST /api/checkout
{
    "product_id": 42,
    "price": 0.01,    // ❌ пользователь сам указал цену
    "quantity": 100
}
```

**Хорошо (сервер берёт цену из БД):**
```python
@app.post('/api/checkout')
def checkout():
    data = request.json
    product = Product.find(data['product_id'])
    # Сервер берёт актуальную цену из БД
    total = product.price * data['quantity']  # ✅
    process_payment(total)
```

### Роль пользователя

**Плохо (роль из запроса):**
```javascript
// Сервер доверяет роли, переданной клиентом
app.post('/api/admin/delete-user', (req, res) => {
    if (req.body.role === 'admin') {  // ❌ кто угодно может передать role: admin
        deleteUser(req.body.userId);
    }
});
```

**Хорошо (роль из session/JWT):**
```javascript
app.post('/api/admin/delete-user', (req, res) => {
    // Сервер сам определяет роль из аутентификации
    const user = getCurrentUser(req);  // из JWT/session
    if (user.role === 'admin') {       // ✅ серверный источник правды
        deleteUser(req.body.userId);
    }
});
```

### Что нельзя доверять? (сводная таблица)

| Параметр | Плохо (доверяет клиенту) | Хорошо (сервер вычисляет) |
|----------|-------------------------|--------------------------|
| **Цена товара** | `{ "price": 10 }` | Сервер берёт цену из БД по product_id |
| **Роль пользователя** | `{ "role": "admin" }` | Сервер определяет роль из JWT/session |
| **Скидка** | `{ "discount": 90 }` | Сервер вычисляет скидку по бизнес-правилам |
| **Стоимость доставки** | `{ "shipping": 0 }` | Сервер рассчитывает по адресу и весу |
| **Итоговая сумма** | `{ "total": 100 }` | Сервер собирает из позиций заказа |
| **ID пользователя** | `{ "userId": 1 }` | Сервер берёт из аутентификации |
| **Tenant ID** | `{ "tenantId": 7 }` | Сервер определяет из контекста |
| **Feature flags** | `{ "isPremium": true }` | Сервер проверяет подписку в БД |
| **Права доступа** | `{ "isAdmin": true }` | Сервер проверяет через IAM/RBAC |
| **Баланс монет** | `{ "coins": 1000000 }` | Сервер сам хранит и рассчитывает баланс |

## Never Trust the Client vs Assume Breach

| | Never Trust the Client | Assume Breach |
|---|---|---|
| **Вопрос** | «Можно ли доверять данным от клиента?» | «Что делать, если клиент уже скомпрометирован?» |
| **Ответ** | Нет, все данные нужно проверять | Ограничивать ущерб: изоляция, audit, forensics |
| **Пример** | Валидация всех input'ов на сервере | Rate limiting, anomaly detection |
| **Связь** | Never Trust the Client — **первый шаг** | Assume Breach — **следующий шаг**, когда защита уже обойдена |

---

## Never Trust the Client в контексте STRIDE

С точки зрения Threat Modeling (STRIDE), Never Trust the Client уменьшает риск:

| Угроза | Как принцип помогает |
|--------|---------------------|
| **Tampering** | Сервер не принимает данные «на веру» — проверяет каждый параметр |
| **Spoofing** | Сервер сам определяет identity пользователя, а не берёт из запроса |
| **Elevation of Privilege** | Роль и права определяются сервером, не клиентом |
| **Information Disclosure** | Сервер вычисляет, какие данные возвращать, а не отдаёт всё, что запросил клиент |

## Never Trust the Client и Zero Trust

Это практически **один и тот же принцип**.

Zero Trust говорит: **Never Trust, Always Verify**.

Never Trust the Client — это применение Zero Trust к взаимодействию клиент-сервер:
- не доверяй данным от клиента;
- проверяй каждый запрос;
- никогда не полагайся на client-side проверки.

---

## Business Logic и Never Trust the Client

Многие уязвимости бизнес-логики возникают именно из-за нарушения этого принципа:

| Уязвимость | Причина |
|------------|---------|
| **Изменение цены** | Сервер доверял цене от клиента |
| **Бесплатная доставка** | Сервер доверял стоимости доставки от клиента |
| **Изменение количества** | Сервер доверял количеству товара |
| **Race Condition** | Сервер предполагал корректное поведение клиента |
| **BOLA/IDOR** | Сервер доверял ID объекта из запроса |

## Архитектурное мышление

Never Trust the Client — фундаментальный принцип Zero Trust.

**Правильный вопрос:**
> «Что произойдёт, если злоумышленник отправит произвольный запрос с данными, которые он сам выбрал?»

**Trade-offs:**
- **Безопасность vs UX** — серверная валидация может быть медленнее клиентской
- **Безопасность vs Performance** — каждая проверка на сервере добавляет latency
- **Convenience vs Trust** — некоторые данные (например, preferred language) — low-risk, можно не проверять так же строго

---

## Security Architect Perspective

> Never Trust the Client — это принцип, который звучит очевидно, но нарушается постоянно. Самая частая причина — спешка: «Давай пока сделаем проверку на фронтенде, а на бэкенде потом добавим». «Потом» не наступает никогда. Вторая причина — false sense of security: «У нас сложный frontend на React, никто не догадается отправить запрос через curl». Догадаются.

### Junior vs Senior мышление

**Junior думает:**
> «Пользователь нажал кнопку.»

**Senior думает:**
> «Сервер получил произвольный HTTP-запрос.»

Это совершенно другой способ смотреть на систему. Senior не спрашивает «что нажал пользователь», он спрашивает «какой запрос получил сервер и можно ли ему доверять?»

Хороший архитектор исходит из того, что client-side проверки вообще не существуют. Если защита есть только на клиенте — её нет. Единственное исключение — данные, которые не влияют на безопасность: тема оформления, язык интерфейса, порядок сортировки в таблице. Но даже их стоит проверять на сервере, хотя бы минимально.

---

## Связь с другими принципами

- **Complete Mediation** — каждый запрос проверяется на сервере независимо
- **Defense in Depth** — серверная проверка — один из слоёв; клиентская — UX, не защита
- **Fail Secure** — при ошибке проверки на сервере — отказ в операции
- **Open Design** — безопасность не должна зависеть от того, что клиентский код скрыт (security through obscurity)

## Common Interview Mistakes

### ❌ Категоричный ответ
> «Никогда, ни при каких обстоятельствах нельзя доверять клиенту. Все client-side проверки бесполезны.»

**Почему это проблема:** Клиентские проверки полезны для UX: мгновенная валидация формы, подсказки, авто-форматирование. Проблема не в том, что они есть, а в том, что **только** они.

**Зрелая формулировка:**
> «Клиентские проверки — это UX. Они улучшают пользовательский опыт, но не защищают от злоумышленника. Серверные проверки — это Security. Они должны быть всегда, независимо от того, есть ли проверки на клиенте или нет. Клиентские проверки — приятное дополнение, но не замена.»

### ❌ Категоричный ответ
> «Если мы используем HTTPS, то данные от клиента защищены — им можно доверять.»

**Почему это проблема:** HTTPS защищает данные в пути (от перехвата), но не защищает от клиента. Пользователь сам отправляет данные — он может отправить что угодно через свой браузер, curl, Postman или Burp Suite.

**Зрелая формулировка:**
> «HTTPS защищает от man-in-the-middle, но не от клиента. Клиент — это небезопасная среда, которой управляет пользователь. HTTPS — про confidentiality в transit, Never Trust the Client — про integrity и authorization на сервере. Это разные вещи.»

### ❌ Категоричный ответ
> «Obfuscation JavaScript кода решит проблему — злоумышленник не сможет понять, как формируется запрос.»

**Почему это проблема:** Obfuscation — это security through obscurity. Определить, как формируется запрос, можно через DevTools, network tab, перехват трафика. Obfuscation замедляет, но не阻止ляет.

**Зрелая формулировка:**
> «Obfuscation — это защита от casual пользователя, не от злоумышленника. Любой, кто умеет пользоваться DevTools, может обойти obfuscation. Единственная настоящая защита — серверная валидация и авторизация. Obfuscation — это дополнительный слой, но не решение.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Почему нельзя доверять данным от клиента?** | Клиент полностью под контролем пользователя. Браузер, мобильное приложение, HTTP-запросы — всё можно изменить. |
| **Какие данные безопасно получать от клиента?** | Те, что не влияют на безопасность: тема оформления, язык, порядок сортировки. Но даже их стоит минимально проверять. |
| **Почему проверка прав только на фронтенде — нарушение?** | Фронтенд — это UX, а не Security. Любой запрос можно отправить через DevTools, curl или Burp Suite. |
| **Как HTTPS связан с Never Trust the Client?** | Никак. HTTPS защищает в пути (confidentiality). Never Trust the Client про trust на сервере (integrity, authorization). Разные вещи. |
| **Что такое Assume Breach и как он связан с Never Trust the Client?** | Never Trust the Client — первый шаг (не доверяем данным). Assume Breach — следующий (предполагаем, что клиент скомпрометирован и ограничиваем ущерб). |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Проверка прав только на UI | Любой запрос через DevTools обходит проверку |
| Валидация только на фронтенде | Злоумышленник отправляет любые payload'ы |
| **Цена/скидка из запроса клиента** | Пользователь может изменить цену |
| **Роль пользователя из тела запроса** | Кто угодно может представиться admin |
| **ID пользователя из запроса** | Можно подставить чужой ID (IDOR) |
| **Tenant ID из запроса** | Cross-tenant data access (BOLA) |
| **Feature flags с клиента** | `{ "isPremium": true }` — получить платный функционал бесплатно |
| Секреты/ключи в JavaScript | Любой может прочитать их из браузера |
| Проверка капчи только на клиенте | Капча — это тоже client-side, её можно обойти |
| Баланс валюты/монет от клиента | Игровой сервер: клиент сам сообщает, сколько монет заработал |

## Lessons Learned

- Клиент — небезопасная среда. Любые данные от клиента — потенциально вредоносны
- Client-side проверки — это UX, не Security
- Сервер — единственное место для проверок безопасности
- Для сервера не существует «честного клиента» — есть только HTTP-запрос
- Это касается не только Web: Android, iOS, Desktop, GraphQL — везде один принцип
- Сервер должен самостоятельно определять: права, роли, стоимость, скидки, tenant, баланс
- HTTPS — про confidentiality, Never Trust the Client — про integrity и authorization
- Obfuscation — не защита, а задержка для злоумышленника
- Assume Breach — следующий шаг после Never Trust the Client
- Если защита есть только на клиенте — **её нет**

> 🎯 **Самая важная мысль:** Любая информация, пришедшая от клиента, должна рассматриваться как недостоверная до тех пор, пока сервер её не проверит или не вычислит самостоятельно.
