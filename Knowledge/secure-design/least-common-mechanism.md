# Secure Design Principle — Least Common Mechanism

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Least Common Mechanism (Минимизация разделяемых механизмов)** — принцип Secure Design, согласно которому следует **минимизировать использование общих механизмов** между разными субъектами, особенно для операций с разными уровнями доверия.

**Основная идея:**
Разделяемый механизм — это общая точка отказа для всех, кто его использует.

---

## Зачем нужен Least Common Mechanism?

Когда несколько субъектов (пользователей, сервисов, процессов) используют один механизм, компрометация этого механизма ставит под угрозу **всех** участников.

**Главная идея:**
> Каждый разделяемый компонент — это potential single point of compromise.

**Пример:**
Если все сервисы используют общий API Gateway, компрометация Gateway даёт доступ ко всем сервисам.
Если у каждого сервиса свой Gateway, компрометация одного не влияет на остальные.

---

## Least Common Mechanism vs Isolation

| | Least Common Mechanism | Полная изоляция |
|---|---|---|
| **Подход** | Минимизировать общие механизмы | Каждый субъект работает в изоляции |
| **Сложность** | Умеренная | Высокая (сложно управлять) |
| **Безопасность** | Выше, чем с общими механизмами | Максимальная |
| **Стоимость** | Ниже полной изоляции | Высокая |
| **Пример** | Разные Service Account для разных сервисов | Каждый сервис в отдельном VPC с собственным Gateway |

## Примеры

### Kubernetes: общий Service Account

**Плохо (общий механизм):**
```yaml
# Все сервисы используют один Service Account
kind: ServiceAccount
name: default
# Компрометация одного сервиса = доступ ко всем
```

**Хорошо (раздельные механизмы):**
```yaml
# У каждого сервиса свой Service Account
kind: ServiceAccount
name: payment-service
---
kind: ServiceAccount
name: notification-service
# Компрометация одного не влияет на другие
```

### API Gateway

**Плохо (один Gateway для всего):**
```
              ┌──────────────┐
Clients ───→  │  API Gateway  │ ───→ payment-service
              │  (общий)      │ ───→ user-service
              └──────────────┘ ───→ notification-service
```

**Хорошо (раздельные Gateway по уровням доверия):**
```
Public Clients ───→ Public Gateway ───→ payment-service
Internal Apps ───→ Internal Gateway ───→ user-service
Admin ──────────→ Admin Gateway ───→ admin-service
```

Разделение по уровням доверия: компрометация Public Gateway не даёт доступ к admin endpoint'ам.

### База данных: общий доступ

**Плохо (все сервисы — одна БД с общим доступом):**
```sql
-- Все сервисы имеют доступ ко всем таблицам
GRANT ALL ON database.* TO 'app'@'%';
```

**Хорошо (своя БД/схема для каждого сервиса):**
```sql
-- Сервис платёжей видит только свою схему
GRANT SELECT, INSERT ON payments.* TO 'payment-svc'@'payment.internal';
-- Сервис пользователей — только свою
GRANT SELECT, INSERT, UPDATE ON users.* TO 'user-svc'@'user.internal';
```

### Multi-tenant SaaS: tenant isolation

**Плохо (один shared bucket для всех):**
```
s3://app-uploads/user1/image.jpg
s3://app-uploads/user2/image.jpg   # tenant B может прочитать tenant A
```

**Хорошо (раздельные buckets/prefixes с политиками):**
```
s3://app-uploads-tenant1/user1/image.jpg
s3://app-uploads-tenant2/user2/image.jpg   # политики запрещают cross-tenant доступ
```

## Архитектурное мышление

Least Common Mechanism — это баланс между безопасностью и operational efficiency.

**Правильный вопрос:**
> «Какие общие механизмы создают риск массовой компрометации? И можем ли мы их изолировать?»

**Trade-offs:**
- **Безопасность vs Cost** — раздельные механизмы дороже (каждый нужно администрировать)
- **Безопасность vs Управляемость** — много изолированных компонентов сложнее управлять
- **Безопасность vs Производительность** — изоляция может добавить latency
- **Isolation vs Sharing** — иногда sharing оправдан (например, общий Redis для кэша), но с чёткими границами

## Security Architect Perspective

> Least Common Mechanism — один из принципов, который стал особенно актуален в эпоху микросервисов и multi-tenant SaaS. Классическая ошибка: сделать «единый сервис авторизации» или «общий gateway» и считать это хорошей архитектурой. Да, это удобно. Но это и единая точка компрометации. Современный подход — разделять не только по функции, но и по уровню доверия: public vs internal vs admin, tenant A vs tenant B. Хороший архитектор всегда помечает общие компоненты как критически важные для безопасности и применяет к ним дополнительные controls: строгий аудит, изоляцию, лимиты. А если можно сделать не общим — делает не общим.

## Least Common Mechanism в микросервисах

Этот принцип неожиданно актуален для микросервисной архитектуры.

| Общий механизм | Риск | Как изолировать |
|----------------|------|----------------|
| Service Account / IAM Role | Компрометация одного сервиса = доступ ко всем | У каждого сервиса своя роль с минимумом прав |
| Shared Database | SQL Injection в одном сервисе = чтение данных других | У каждого сервиса своя схема или своя БД |
| Shared Message Queue | Один сервис может читать чужие сообщения | Отдельные queue/topic для каждого сервиса |
| Shared Secret Store | Один сервис может получить секреты других | Разделение по policy: каждый сервис видит только свои secrets |
| API Gateway | Компрометация Gateway = контроль над всеми endpoint'ами | Раздельные Gateway по уровням доверия |

---

## Связь с другими принципами

- **Defense in Depth** — изоляция механизмов — дополнительный слой защиты
- **Least Privilege** — определяет, какие права давать каждому изолированному компоненту
- **Reduce Attack Surface** — изоляция уменьшает поверхность, доступную при компрометации одного компонента
- **Economy of Mechanism** — противоречие: изоляция увеличивает сложность, но уменьшает риски

## Common Interview Mistakes

### [NO] Категоричный ответ
> «Микросервисы нарушают Least Common Mechanism, потому что много сервисов = много общих компонентов.»

**Почему это проблема:** Микросервисы не нарушают принцип, они его **реализуют**. В монолите все функции разделяют один процесс, одну память, одну БД — это максимальное нарушение Least Common Mechanism. Микросервисы, наоборот, изолируют функции друг от друга.

**Зрелая формулировка:**
> «Микросервисы — это практическая реализация Least Common Mechanism: каждый сервис изолирован, имеет свою БД/схему, свой Service Account, свои секреты. Проблема возникает, когда микросервисы начинают использовать общие компоненты без изоляции: общий Gateway, общая очередь, общая БД. Тогда компрометация одного сервиса может затронуть другие.»

### [NO] Категоричный ответ
> «Всегда нужно изолировать всё. Каждый сервис — отдельный VPC, отдельный Gateway, отдельная БД.»

**Почему это проблема:** Полная изоляция — это дорого и сложно в управлении. Часто неоправданно для сервисов с низким уровнем чувствительности.

**Зрелая формулировка:**
> «Изоляция должна быть пропорциональна риску. Критичные сервисы (payments, auth) — максимально изолированы. Вспомогательные (notifications, logging) — могут использовать общие механизмы, но с чёткими границами и мониторингом. Принцип — минимизировать, а не исключать общие механизмы.»

### [NO] Категоричный ответ
> «Shared nothing architecture — единственный безопасный подход.»

**Почему это проблема:** «Shared nothing» идеалистичен. В реальности всегда есть общие механизмы: DNS, мониторинг, CI/CD, logging. Важно не исключить их полностью, а осознанно управлять рисками.

**Зрелая формулировка:**
> «Shared nothing — это цель, но не абсолют. В реальности общие механизмы неизбежны. Важно: 1) Идентифицировать общие компоненты; 2) Оценить риск массовой компрометации; 3) Применить compensating controls (аудит, мониторинг, лимиты); 4) Изолировать там, где риск неприемлем.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Что такое Least Common Mechanism?** | Принцип, согласно которому следует минимизировать использование общих механизмов между разными субъектами, чтобы компрометация одного не затронула других. |
| **Почему общий Service Account в Kubernetes — нарушение?** | Компрометация одного пода/сервиса даёт доступ к ресурсам, которые используют этот Service Account. Каждый сервис должен иметь свой account. |
| **Как Least Common Mechanism применяется в multi-tenant системах?** | Изоляция данных tenant'ов: отдельные БД/schemas, отдельные buckets, отдельные encryption keys. Компрометация tenant A не должна дать доступ к данным tenant B. |
| **Как сбалансировать изоляцию и стоимость?** | Критичные сервисы — максимальная изоляция. Некритичные — общие механизмы с compensating controls (audit, rate limiting, monitoring). |
| **Чем отличаются shared database и shared nothing?** | Shared database — все сервисы используют одну БД (высокий риск). Shared nothing — каждый сервис имеет свою БД (изоляция). |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Один Service Account для всех сервисов в Kubernetes | Компрометация одного пода = доступ ко всем ресурсам |
| Все сервисы используют общую БД | SQL Injection в одном сервисе = чтение данных других |
| Один API Gateway для public и admin endpoint'ов | Компрометация public части может дать доступ к admin |
| Shared очередь для всех типов сообщений (включая sensitive) | Один consumer может читать чужие сообщения |
| Shared secret store без изоляции по policy | Любой сервис может получить любой секрет |

---

## Lessons Learned

- Каждый разделяемый механизм — potential single point of compromise
- Компрометация общего компонента ставит под угрозу **всех**, кто его использует
- Изоляция должна быть пропорциональна риску (risk-based, не absolute)
- Микросервисы — реализация Least Common Mechanism, если они правильно изолированы
- Если общий механизм неизбежен — применяй compensating controls (audit, лимиты, мониторинг)
- Разделяй не только по функции, но и по уровню доверия
