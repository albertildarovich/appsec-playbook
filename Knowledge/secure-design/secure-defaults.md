# Secure Design Principle — Secure Defaults (Secure by Default)

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Secure Defaults (Secure by Default)** — принцип Secure Design, согласно которому система должна быть безопасной сразу после установки или создания, без необходимости дополнительной настройки безопасности.

**Основная идея:**
Если пользователь, администратор или разработчик ничего не настроили, система всё равно должна оставаться безопасной.

---

## Зачем нужен Secure Defaults?

Большинство инцидентов связано не с отсутствием механизмов защиты, а с **ошибками конфигурации**.

Люди:
- забывают включить TLS;
- оставляют стандартные пароли;
- не отключают Debug Mode;
- выдают избыточные права.

Secure Defaults снижает вероятность подобных ошибок.

**Главная идея:**
> Хороший разработчик думает: «Администратор может ошибиться.»
> Хороший AppSec-инженер думает: «Администратор **обязательно** когда-нибудь ошибётся.»
>
> Поэтому безопасные настройки должны применяться **автоматически**.

---

## Secure Defaults vs Maximum Security

| | Secure Defaults | Maximum Security |
|---|---|---|
| **Подход** | Безопасно для типового сценария | Запретить всё, что можно запретить |
| **Риск** | Может быть недостаточно для высоких требований | Пользователи начнут обходить ограничения |
| **Пример** | Spring Security: HTTPS + CSRF включены по умолчанию | Все порты закрыты, любой запрос требует multi-factor |

Secure Defaults ≠ Максимально строгие настройки. Излишне жёсткие ограничения приводят к тому, что пользователи массово обходят механизмы безопасности.

## Примеры

### AWS S3

**Раньше:** Новые Bucket'ы можно было сделать публичными по ошибке.

**Сейчас:** Публичный доступ по умолчанию заблокирован. Администратор должен явно открыть доступ.

### Spring Security

После подключения Spring Security:
- [OK] Требуется аутентификация
- [OK] CSRF включён
- [OK] Базовые защитные механизмы применяются

**Безопасность включена по умолчанию.**

### Kubernetes

Новые рабочие нагрузки должны запускаться с безопасными настройками:
- [OK] Ограниченные Service Account
- [OK] Pod Security Standards
- [OK] Минимально необходимые привилегии

### Политика паролей

**Небезопасно (нет Secure Defaults):**
```javascript
// Минимальная длина пароля — 1 символ
// Администратор должен сам усилить требования
{ minLength: 1 }
```

**Безопасно (Secure Defaults):**
```javascript
// Разумная минимальная длина
// Защита от слабых паролей включена по умолчанию
{ minLength: 8, requireSpecialChar: true, requireNumber: true }
```

### Debug Mode

**Плохо:**
```python
# DEBUG = True по умолчанию
# Разработчик должен не забыть выключить перед релизом
DEBUG = True
```

**Хорошо:**
```python
# DEBUG = False по умолчанию
# Разработчик явно включает для отладки
DEBUG = os.getenv('DEBUG', 'False') == 'True'
```

## Архитектурное мышление

Secure Defaults — это не "запретить всё". Это про **разумный баланс** между безопасностью и usability.

**Правильный вопрос:**
> Какие настройки будут безопасными для 80% пользователей, но не настолько жёсткими, чтобы они начали их обходить?

**Trade-offs:**
- **Безопасность vs Удобство** — слишком строгие настройки заставляют пользователей искать обходные пути
- **Generic vs Specific** — универсальные настройки безопаснее, но могут мешать специфическим сценариям
- **User Experience vs Protection** — лишние шаги при регистрации снижают конверсию

---

## Security Architect Perspective

> В реальных проектах Secure Defaults — это постоянный компромисс между security и product. Слишком жёсткие настройки по умолчанию заставляют разработчиков создавать "whitelist exceptions" или вообще отключать защиту "чтобы не мешала". Лучшая стратегия — сделать безопасные настройки по умолчанию, но предоставить чёткий и документированный механизм их изменения для тех сценариев, где это действительно нужно. Хороший архитектор всегда скажет: «По умолчанию — безопасно. Хочешь изменить — объясни почему и зафиксируй исключение в ADR.»

---

## Связь с другими принципами

- **Least Privilege** — новые пользователи получают минимальные права
- **Fail Secure** — при отсутствии настройки система выбирает безопасное поведение
- **Reduce Attack Surface** — ненужные функции и интерфейсы отключены по умолчанию
- **Defense in Depth** — безопасные настройки — первый слой защиты

## Common Interview Mistakes

### [NO] Категоричный ответ
> «Нужно всё запретить по умолчанию. Максимально строгие настройки — единственный правильный подход.»

**Почему это проблема:** Излишне жёсткие ограничения приводят к shadow security — пользователи находят обходные пути, которые никто не контролирует. Например, если пароль должен содержать 25 символов с тремя спецсимволами — пользователи запишут его на стикере и приклеят к монитору.

**Зрелая формулировка:**
> «Secure Defaults — это баланс. Настройки должны быть безопасными для 80% типовых сценариев, но не настолько жёсткими, чтобы провоцировать обход. Для оставшихся 20% должен быть документированный процесс изменения с фиксацией в ADR.»

### [NO] Категоричный ответ
> «Debug Mode в Production — это всегда катастрофа. Никогда, ни при каких обстоятельствах.»

**Почему это проблема:** Бывают ситуации, когда debug временно необходим (диагностика production-инцидента). Проблема не в самом Debug Mode, а в отсутствии контроля: кто включил, когда, почему, и когда выключит.

**Зрелая формулировка:**
> «Debug Mode в Production — это высокий риск, но иногда оправданный. Важно: 1) Secure Default — DEBUG=False; 2) Включение требует approval; 3) Автоматическое отключение через N минут; 4) Audit log каждого включения. Проблема не в действии, а в отсутствии процесса.»

### [NO] Категоричный ответ
> «Secure by Default означает, что все настройки администратора должен задать сам, потому что только он знает, что нужно его системе.»

**Почему это проблема:** Это перекладывает ответственность за безопасность на админа, который может ошибиться, устать или просто не знать о best practices.

**Зрелая формулировка:**
> «Secure by Default означает, что система безопасна без дополнительных действий администратора. Администратор может усилить настройки, но не должен делать их безопасными с нуля. Это сдвиг ответственности: не «админ должен настроить безопасность», а «система должна быть безопасной, даже если админ ничего не настроил».»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Почему Spring Security требует аутентификацию сразу после подключения?** | Это Secure by Default: безопасность включена по умолчанию, разработчик явно настраивает исключения. |
| **Почему новые IAM-пользователи не должны получать права администратора?** | Least Privilege + Secure Defaults: новые пользователи получают минимум прав, администратор явно повышает при необходимости. |
| **Почему новая функциональность должна быть отключена до завершения тестирования?** | Reduce Attack Surface: ненужные функции отключены по умолчанию, снижая поверхность атаки. |
| **Что означает принцип Secure by Default?** | Система безопасна «из коробки». Пользователь/администратор не должен настраивать безопасность — она уже включена. |
| **Чем Secure Defaults отличается от Maximum Security?** | Secure Defaults — безопасно для типового сценария. Maximum Security — запретить всё (часто приводит к обходу). |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Debug Mode включён в Production | Информация о системе доступна злоумышленнику |
| Стандартные учётные записи не удалены (admin/admin) | Первое, что пробует злоумышленник |
| Открытые административные панели (Grafana, Jenkins) | Доступ к управлению без аутентификации |
| Пользователи получают избыточные права сразу после регистрации | Нарушение Least Privilege |
| TLS не включён по умолчанию | Трафик передаётся в открытом виде |

---

## Lessons Learned

- Большинство проблем безопасности возникает из-за ошибок конфигурации, а не отсутствия защитных механизмов
- Безопасные значения должны применяться **автоматически**, а не ждать, пока администратор их настроит
- Secure Defaults помогает уменьшить влияние человеческого фактора
- Излишне жёсткие настройки провоцируют обход — ищи баланс
- Принцип тесно связан с Least Privilege, Fail Secure и Reduce Attack Surface
- Фиксируй исключения из Secure Defaults в ADR — чтобы было понятно, почему и кем принято решение
