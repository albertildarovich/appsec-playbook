# Secure Design Principle — Psychological Acceptability

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Psychological Acceptability (Психологическая приемлемость)** — принцип Secure Design, согласно которому механизмы безопасности должны быть **понятными, удобными и естественными** для пользователей, чтобы они не пытались их обходить.

**Основная идея:**
Безопасность должна помогать пользователю, а не бороться с ним.

---

## Зачем нужен этот принцип?

Даже самая надёжная система безопасности не принесёт пользы, если пользователи будут искать способы её обойти.

Например:
- записывать сложные пароли на стикерах;
- отключать MFA;
- передавать токены коллегам;
- использовать один пароль везде;
- хранить секреты в Git.

**Во всех этих случаях проблема не только в пользователе — проблема в дизайне системы.**

**Главная идея:**
> Перед внедрением механизма безопасности стоит спросить: «Не вынуждает ли этот механизм пользователей искать обходные пути?»

---

## Psychological Acceptability vs Security Maximalism

| | Psychological Acceptability | Security Maximalism |
|---|---|---|
| **Подход** | Безопасность удобна по умолчанию | Максимум ограничений любой ценой |
| **Пользователь** | Следует безопасному пути, потому что это удобно | Ищет обходные пути |
| **Результат** | Высокий compliance, меньше инцидентов | Shadow security, MFA Fatigue, стикеры с паролями |
| **Пример** | Password manager + passphrase | Пароль 32 символа, смена каждые 30 дней |

## Примеры

### Пример №1. Password Policy

**Плохо (Security Maximalism):**
```javascript
// Политика, которая вынуждает пользователей обходить
{
    minLength: 32,
    requireSpecialChar: true,
    requireNumber: true,
    requireUppercase: true,
    expireEvery: 30,  // дней
    forbidPasswordManager: true  // 😱
}
```
**Результат:** `Password123!` → `Password124!` → `Password125!` Или пароль на стикере.

**Хорошо (Psychological Acceptability):**
```javascript
{
    minLength: 12,
    encouragePassphrase: true,
    allowPasswordManager: true,
    expireOnlyOnCompromise: true,
    requireMFA: true
}
```
**Результат:** Пользователь использует менеджер паролей + MFA. Реальная безопасность выше.

### Пример №2. MFA Fatigue

**Плохо — MFA на каждое действие:**
```
Вход в систему → MFA
Открыть email → MFA
Скачать файл → MFA
Посмотреть настройки → MFA
```
Пользователь начинает нажимать «Подтвердить» **автоматически** — это MFA Fatigue.

**Хорошо — MFA только на рискованные операции:**
```
Вход с нового устройства → MFA
Смена пароля → MFA
Изменение email → MFA
Перевод крупной суммы → MFA
Просмотр профиля → ❌ (без MFA)
```
Дополнительные проверки появляются только для действительно рискованных операций.

### Пример №3. Git Security Checks

**Плохо (ручные проверки):**
```
Перед каждым коммитом разработчик вручную запускает:
1. SAST
2. DAST
3. SCA
4. Secret Scan
5. License Scan
```
Разработчики начнут пропускать шаги или автоматизируют их небезопасным способом.

**Хорошо (автоматизировано):**
```
Все проверки запускаются автоматически в CI/CD.
Разработчику не нужно помнить о них.
```

### Пример №4. Kubernetes Logs

**Плохо (сложный процесс):**
```
1. Заполнить форму доступа
2. Дождаться approval (2 дня)
3. Подключиться через VPN
4. Выполнить 10 команд
5. Не забыть отозвать доступ
```
Разработчики: «Дайте нам общий admin-аккаунт, чтобы не ждать».

**Хорошо (удобный процесс):**
```
RBAC с минимальными правами + удобный UI для логов.
Доступ выдаётся автоматически через SSO + group membership.
```

### Пример №5. Vault

**Плохо (сложный процесс получения секрета):**
Разработчики копируют секреты в `.env` или в GitHub Secrets без контроля.

**Хорошо (автоматическая выдача):**
Секреты автоматически выдаются через Vault Agent или Workload Identity. Разработчик даже не думает о том, где взять секрет — он уже есть в окружении.

## Архитектурное мышление

**Junior говорит:**
> «Чем больше ограничений, тем безопаснее.»

**Senior спрашивает:**
> «Что будут делать пользователи, если эти ограничения начнут мешать их работе?»

**Правильный вопрос:**
> «Как сделать безопасный путь самым простым и удобным?»

**Trade-offs:**
- **Безопасность vs Удобство** — слишком жёсткие меры провоцируют обход
- **Control vs Automation** — ручной контроль формально строже, но на практике менее эффективен
- **Security vs Productivity** — если безопасность замедляет работу, её будут обходить

---

## Security Architect Perspective

> Psychological Acceptability — это принцип, который отличает зрелую AppSec-культуру от формального соблюдения требований. Можно заставить разработчиков вручную запускать десять инструментов перед каждым коммитом. Формально это повысит контроль. На практике — часть проверок будут забывать, часть — обходить, а безопасность превратится в препятствие. Гораздо лучше встроить проверки в CI/CD так, чтобы безопасный процесс был одновременно самым простым. Именно поэтому современные DevSecOps-подходы так активно делают ставку на автоматизацию: она снижает вероятность человеческой ошибки и уменьшает желание обходить механизмы безопасности. Хороший архитектор не спрашивает «как заставить разработчиков», он спрашивает «как сделать так, чтобы безопасный путь был также путём наименьшего сопротивления».

---

## Psychological Acceptability ≠ Снижение безопасности

Это **самое распространённое заблуждение**.

Принцип **не говорит:**
> «Сделайте безопасность слабее.»

Он **говорит:**
> Сделайте **безопасный путь** самым простым и удобным.

| Вместо этого | Делаем это |
|-------------|-----------|
| Ручная ротация сертификатов | Автоматическая ротация (Let's Encrypt) |
| Десятки отдельных паролей | SSO |
| Ручной Secret Scanning | Автоматический (Gitleaks в CI/CD) |
| Сложные пароли + смена 30 дней | Passphrase + MFA |
| MFA на каждое действие | MFA только на рискованные операции |

---

## Связь с другими принципами

- **Secure Defaults** — безопасная конфигурация должна быть удобной сразу после установки
- **Economy of Mechanism** — простые механизмы легче понять и правильно использовать
- **Fail Secure** — ошибки не должны превращать систему в неудобную или неработоспособную без причины
- **Never Trust the Client** — пользователь не обязан помнить все правила безопасности — система должна автоматически проверять критичные вещи

## Common Interview Mistakes

### ❌ Категоричный ответ
> «Безопасность и удобство несовместимы. Чем безопаснее — тем менее удобно. Пользователи должны терпеть.»

**Почему это проблема:** Это классическое заблуждение. Если безопасность слишком неудобна, пользователи найдут обходные пути, которые будут менее безопасны, чем если бы система была спроектирована с учётом Psychological Acceptability.

**Зрелая формулировка:**
> «Безопасность и удобство — это не always-sum game. Хороший дизайн может сделать безопасность удобной: автоматическая ротация сертификатов удобнее ручной, SSO удобнее десятка паролей, CI/CD удобнее ручных проверок. Задача — не выбирать между безопасностью и удобством, а проектировать так, чтобы безопасный путь был путём наименьшего сопротивления.»

### ❌ Категоричный ответ
> «Разработчики должны следовать процессам безопасности. Если они их обходят — это их проблема, нужно усилить контроль.»

**Почему это проблема:** Если процессы обходят систематически — проблема в процессах, а не в разработчиках. Люди всегда ищут путь наименьшего сопротивления. Задача AppSec — сделать безопасный путь самым простым.

**Зрелая формулировка:**
> «Если разработчики систематически обходят процесс безопасности — это сигнал, что процесс неудобен. Усиление контроля только усугубит проблему: появятся shadow IT, недокументированные обходы, общие учётки. Вместо этого нужно перепроектировать процесс: автоматизировать, упростить, встроить в инструменты, которыми разработчики уже пользуются.»

### ❌ Категоричный ответ
> «Пароль должен быть максимально сложным и меняться каждые 30 дней. Это базовый best practice.»

**Почему это проблема:** NIST SP 800-63B уже много лет рекомендует отойти от этой практики. Частая смена паролей приводит к предсказуемым паттернам (Password1! → Password2!), а сложность — к записи на стикерах.

**Зрелая формулировка:**
> «Современные рекомендации (NIST SP 800-63B) — длинные парольные фразы (passphrase), смена только при подозрении на компрометацию, обязательный MFA. Исследования показывают, что политика «32 символа + смена 30 дней» приводит к менее безопасному поведению, чем passphrase + MFA без принудительной смены.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Что означает Psychological Acceptability?** | Механизмы безопасности должны быть понятными, удобными и естественными, чтобы пользователи не пытались их обходить. |
| **Почему слишком сложная политика паролей может снизить безопасность?** | Пользователи начинают записывать пароли, использовать предсказуемые паттерны (Password1! → Password2!), делиться учётками. |
| **Почему автоматизация повышает безопасность?** | Автоматизация делает безопасный путь самым простым. Разработчику не нужно помнить о проверках — они происходят сами. |
| **Что такое MFA Fatigue и как с ним бороться?** | Пользователь настолько часто подтверждает MFA, что начинает делать это автоматически. Решение: MFA только на рискованные операции, number matching, contextual MFA. |
| **Почему разработчики иногда обходят процессы безопасности?** | Потому что процессы неудобны. Если обход безопаснее/быстрее/проще официального процесса — будут обходить. |

## Реальные примеры (Psychological Acceptability в действии)

| Продукт | Что делает | Почему это Psychological Acceptability |
|---------|------------|--------------------------------------|
| **GitHub Code Scanning** | Автоматически сканирует код в PR | Разработчику не нужно помнить о SAST |
| **Google Chrome** | Автоматически обновляется | Пользователю не нужно думать о patching |
| **Let's Encrypt** | Автоматически выпускает и продлевает сертификаты | Разработчику не нужно помнить о ротации |
| **GitHub Dependabot** | Автоматически предлагает обновления зависимостей | Разработчику не нужно проверять уязвимости вручную |
| **Vault Agent** | Автоматически выдаёт краткоживущие секреты | Разработчик не копирует секреты в .env |
| **SSO (Okta, Google Workspace)** | Один вход во все сервисы | Пользователь не запоминает N паролей |

Во всех этих случаях **безопасное поведение становится поведением «по умолчанию»**.

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Слишком сложные требования к паролям | Пользователи записывают их на стикерах |
| MFA для каждой операции | MFA Fatigue — подтверждение автоматически |
| Сложный процесс получения доступа | Разработчики делятся учётными записями |
| Ручные проверки безопасности | Забывают или сознательно пропускают |
| Неудобные процессы | Появляются «временные» обходные решения, которые остаются навсегда |

---

## Lessons Learned

- Пользователи всегда стремятся выбрать **самый удобный путь**
- Если безопасный путь слишком сложен — появятся **небезопасные обходные решения**
- Проблема не только в пользователе — проблема в **дизайне системы**
- Автоматизация и удобство **часто повышают безопасность**, а не снижают
- Хорошая система безопасности делает **правильное действие самым простым**
- Psychological Acceptability — это не «сделать безопасность слабее», а «сделать безопасный путь удобным»
- Этот принцип отличает зрелую AppSec-культуру от формального compliance
