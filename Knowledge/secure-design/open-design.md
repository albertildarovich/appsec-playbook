# Secure Design Principle — Open Design

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Open Design** — принцип Secure Design, согласно которому безопасность системы **не должна зависеть от секретности** её реализации, алгоритмов или архитектуры.

**Основная идея:**
Даже если злоумышленник знает, как устроена система, она должна оставаться безопасной.

---

## Зачем нужен Open Design?

Любая современная система может быть исследована:
- изучен JavaScript в браузере (DevTools);
- декомпилировано мобильное приложение (JADX, Frida);
- проанализирован сетевой трафик (Wireshark, Burp);
- исследованы API (документация, fuzzing);
- проанализированы бинарные файлы (Ghidra, IDA).

Поэтому безопасность должна строиться **не на сокрытии реализации**, а на надёжных механизмах защиты.

**Главная идея:**
> Перед проектированием системы стоит исходить из предположения: злоумышленник знает архитектуру, API, алгоритмы и используемые технологии.

---

## Open Design vs Security through Obscurity

| | Open Design | Security through Obscurity |
|---|---|---|
| **Подход** | Безопасность на механизмах защиты | Безопасность на сокрытии информации |
| **Зависит от** | Ключей, токенов, паролей | Того, что злоумышленник "не догадается" |
| **Пример** | JWT с проверкой подписи на сервере | Скрытый URL `/admin-secret-938472` |
| **При компрометации** | Нужен ключ/токен — система защищена | Система полностью открыта |
| **Принцип** | «Система безопасна, даже если устройство известно» | «Система безопасна, пока никто не знает, как она устроена» |

---

## Что должно быть секретом, а что — нет?

### Секретами должны оставаться **только**:
- пароли;
- криптографические ключи;
- токены (access, refresh);
- секреты Vault;
- HMAC-ключи;
- приватные сертификаты.

### Что **НЕ должно быть секретом**:
| Компонент | Почему не секрет |
|-----------|-----------------|
| Алгоритмы (AES, RSA, SHA) | Публичные стандарты, их нельзя менять |
| Структура JWT | header.payload.signature — всем известна |
| OAuth Flow | Публичный протокол RFC |
| Формат API | Злоумышленник найдёт через fuzzing или документацию |
| Используемые библиотеки | Определяются по ошибкам, заголовкам, fingerprinting |
| Архитектурные решения | Reverse engineering, публичные доклады |

**Если раскрытие этой информации делает систему небезопасной — архитектура построена неправильно.**

## Примеры

### Криптография

**Плохо (security through obscurity):**
```python
# Собственный алгоритм шифрования
def encrypt(data):
    result = []
    for byte in data:
        result.append(byte ^ my_secret_table[byte % 256])  # 
    return bytes(result)
```

**Хорошо (Open Design):**
```python
# Публичный алгоритм, секретный — только ключ
from cryptography.fernet import Fernet
cipher = Fernet(key)  # [OK] AES известен всем, секретен только ключ
encrypted = cipher.encrypt(data)
```

### JWT

**Плохо:**
```javascript
// Надежда, что злоумышленник не знает структуру JWT
// "Мы используем собственную вариацию JWT, никто не догадается"
```

**Хорошо:**
```javascript
// Стандартный JWT — структура известна всем
// Безопасность обеспечивается подписью и секретным ключом
jwt.verify(token, secretKey);  // [OK]
```

### Защита админ-панели

**Плохо (только скрытый URL):**
```javascript
// "Никто не догадается"
app.get('/admin-3f8a2b', (req, res) => {
    // [NO] Нет аутентификации, нет авторизации
    res.send(adminPanel);
});
```

**Хорошо (Open Design — URL известен, но защита есть):**
```javascript
// URL может быть любым — защита не в нём
app.get('/admin', authenticate, authorize('admin'), (req, res) => {
    // [OK] Аутентификация + авторизация
    res.send(adminPanel);
});
```

### JavaScript клиент

**Нельзя хранить на клиенте:**
- бизнес-логику (цены, скидки);
- проверки авторизации;
- API Keys;
- криптографические ключи.

Код клиента всегда можно изучить через DevTools.

## Open Design vs Open Source

Это **распространённое заблуждение**.

| | Open Design | Open Source |
|---|---|---|
| **Что требуется** | Безопасность не зависит от секретности реализации | Исходный код доступен публично |
| **Код** | Может быть закрытым | Открыт |
| **Обязательность** | Всегда рекомендуется для безопасности | Зависит от бизнес-модели |
| **Пример** | Закрытый код, но безопасность на механизмах | Linux — код открыт, безопасность на механизмах |

**Open Design не требует открывать исходный код.** Он требует другого: даже если исходный код станет известен злоумышленнику, безопасность системы не должна зависеть от его секретности.

---

## Open Design vs Information Disclosure

**Очень важное различие**, которое часто путают.

| | Open Design | Information Disclosure |
|---|---|---|
| **Говорит** | «Не рассчитывай, что злоумышленник ничего не знает» | «Не помогай злоумышленнику узнать больше, чем необходимо» |
| **Вопрос** | «Что будет, если архитектура известна?» | «Какую лишнюю информацию мы отдаём?» |
| **Пример** | API endpoint'ы известны, но защищены auth | Не показывать stack trace с внутренними путями |

**На практике:**
- скрывать stack traces;
- не раскрывать версии ПО;
- отключать banner disclosure;
- не публиковать внутренние IP;
- не раскрывать внутреннюю архитектуру без необходимости.

**Но:** даже если злоумышленник всё это узнает, безопасность системы **не должна исчезнуть**.

## Архитектурное мышление

Open Design требует двух вопросов одновременно:

1. **Open Design:** «Что произойдёт, если злоумышленник знает, как устроена система?»
2. **Information Disclosure:** «Не раскрываем ли мы сами информацию, которая упрощает ему атаку?»

**Правильный вопрос:**
> «Может ли злоумышленник обойти защиту, если узнает, как устроена система? Если да — это не Open Design.»

**Trade-offs:**
- **Security через obscurity vs Open Design** — скрытый URL даёт ложное чувство безопасности
- **Информация vs Защита** — чем больше известно о системе, тем точнее атака; но защита не должна от этого зависеть
- **Convenience vs Secrecy** — иногда проще скрыть, чем защитить; но это не решение

## Security Architect Perspective

> Open Design — это принцип, который звучит как академическая теория, но имеет очень практическое применение. Когда я вижу admin-панель по «секретному» URL без аутентификации — я знаю, что её взломают. Когда слышу «у нас свой протокол шифрования» — я знаю, что в нём ошибки. Open Design заставляет проектировать защиту так, как будто чертежи системы лежат на GitHub. И это меняет всё: вместо «спрячем этот endpoint» ты начинаешь думать «как защитить этот endpoint, если о нём знают все». Хороший архитектор не полагается на то, что злоумышленник не найдёт — он исходит из того, что злоумышленник уже знает всё, и строит защиту исходя из этого.

---

## Связь с другими принципами

- **Complete Mediation** — каждый запрос проверяется независимо от того, известен ли API
- **Defense in Depth** — даже если злоумышленник знает архитектуру, остаются другие уровни защиты
- **Economy of Mechanism** — использование стандартных и хорошо изученных механизмов обычно безопаснее собственных решений
- **Never Trust the Client** — клиентская логика считается полностью доступной атакующему
- **Reduce Attack Surface** — открытость дизайна не означает открытость всех функций; минимизируем то, что доступно

## Common Interview Mistakes

### [NO] Категоричный ответ
> «Open Design — это то же самое, что Open Source. Если код закрыт — принцип не применим.»

**Почему это проблема:** Open Design не про открытый код. Он про то, что безопасность не должна зависеть от секретности реализации. Закрытый код может полностью соответствовать Open Design, если его безопасность основана на механизмах, а не на секретности.

**Зрелая формулировка:**
> «Open Design и Open Source — разные вещи. Open Design — это подход к архитектуре: даже если злоумышленник знает, как устроена система, она должна оставаться безопасной. Open Source — это лицензионная модель. Можно иметь закрытый код, соответствующий Open Design, и открытый код, нарушающий его (если безопасность зависит от скрытия логики).»

### [NO] Категоричный ответ
> «Нужно скрывать абсолютно всё: версии, banner, заголовки, URL. Если злоумышленник ничего не знает — он не сможет атаковать.»

**Почему это проблема:** Это Security through Obscurity. Злоумышленник всё равно узнает: через fingerprinting, fuzzing, анализ ошибок, публичные CVE. Скрытие информации — это delaying tactic, не защита.

**Зрелая формулировка:**
> «Скрытие информации полезно как практика Information Disclosure — не помогай злоумышленнику без необходимости. Но это не защита. Настоящая защита — в механизмах: аутентификация, авторизация, валидация. Они должны работать, даже если злоумышленник знает версию Nginx и список используемых библиотек.»

### [NO] Категоричный ответ
> «Мы не документируем API — значит злоумышленник не узнает, как его вызвать.»

**Почему это проблема:** API находится в production. Злоумышленник может:
- прочитать frontend код (DevTools);
- перехватить трафик (Burp);
- запустить fuzzing по известным паттернам;
- прочитать документацию (Swagger может быть случайно опубликован).

**Зрелая формулировка:**
> «Недокументированное API — это не защита, а бомба замедленного действия. Его найдут раньше, чем вы успеете защитить. API должен быть защищён независимо от того, документирован он или нет. Open Design предполагает, что endpoint'ы известны, а защита — в механизмах, а не в их секретности.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Что такое Open Design?** | Принцип, согласно которому безопасность системы не должна зависеть от секретности её реализации, алгоритмов или архитектуры. |
| **Чем Open Design отличается от Open Source?** | Open Design — про подход к безопасности (не полагаться на секретность). Open Source — про лицензию (код открыт). Закрытый код может соответствовать Open Design, открытый — нарушать его. |
| **Что такое Security through Obscurity?** | Подход, при котором безопасность основана на сокрытии информации: «никто не догадается». Не работает, потому что злоумышленники находят. |
| **Почему не стоит разрабатывать собственную криптографию?** | Она не будет соответствовать Open Design — безопасность будет зависеть от того, что алгоритм неизвестен. Стандартные алгоритмы (AES, RSA) прошли аудит. |
| **Почему скрытый URL /admin не является механизмом защиты?** | Потому что URL можно найти (fuzzing, документация, DevTools). Настоящая защита — аутентификация + авторизация, которые работают независимо от известности URL. |
| **Нужно ли скрывать версии ПО, если Open Design предполагает, что злоумышленник всё знает?** | Да, это Information Disclosure — не помогай злоумышленнику. Но безопасность не должна зависеть от этой скрытности. Скрытие версий — delaying tactic, не защита. |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Самописная криптография | Безопасность зависит от секретности алгоритма — а алгоритм будет раскрыт |
| Защита админ-панели только «секретным» URL | URL найдётся через fuzzing, документацию, DevTools |
| Надежда на минификацию JavaScript | DevTools показывает оригинальный код (с небольшими искажениями) |
| Хранение секретов в клиентском коде | Любой может прочитать через браузер |
| Отсутствие авторизации, потому что «этот API никто не найдёт» | API найдётся (fuzzing, перехват, документация) |
| Надежда, что obfuscation защитит бизнес-логику | Obfuscation замедляет, но не предотвращает reverse engineering |

## Lessons Learned

- Безопасность должна строиться на проверенных механизмах, а не на сокрытии реализации
- Секретами должны быть **только** секреты: ключи, токены, пароли и сертификаты
- Open Design ≠ Open Source (про разные вещи)
- Open Design ≠ Information Disclosure (не противоречат, а дополняют)
- Не помогай атакующему, раскрывая лишнюю информацию (Information Disclosure)
- Но не рассчитывай, что он её не узнает самостоятельно (Open Design)
- Предположение «атакующий знает устройство системы» делает архитектуру значительно более устойчивой
- Самый опасный подход: "этот endpoint никто не найдёт" — найдёт
- Хорошая архитектура не зависит от секретности, но при этом не раскрывает лишнего
