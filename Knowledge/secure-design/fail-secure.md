# Secure Design Principle — Fail Secure (Fail Closed)

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Fail Secure** — принцип Secure Design, согласно которому при возникновении ошибки система должна перейти в безопасное состояние, а не продолжить выполнение потенциально небезопасной операции.

**Основная идея:**
Лучше временно отказать в выполнении операции, чем случайно нарушить модель безопасности.

---

## Зачем нужен Fail Secure?

Любая система рано или поздно сталкивается с ошибками:
- таймауты;
- недоступность сервисов;
- ошибки сети;
- исключения в коде;
- сбои базы данных;
- ошибки проверки прав.

В этот момент система должна принять решение: **что делать дальше?**

Fail Secure предполагает, что при невозможности безопасно подтвердить операцию система должна её отклонить.

---

## Fail Secure vs Fail Open

| | Fail Secure (Fail Closed) | Fail Open |
|---|---|---|
| **Что происходит** | При ошибке доступ **запрещается** | При ошибке система **продолжает работу** |
| **Примеры** | OAuth Provider недоступен → пользователь не входит; ошибка проверки JWT → запрос отклоняется | WAF недоступен → трафик проходит; сервис рекомендаций недоступен → основной функционал работает |
| **Плюсы** | Сохраняется конфиденциальность и целостность; злоумышленник не получает преимущество из-за ошибки | Сохраняется доступность |
| **Минусы** | Страдает **доступность** сервиса | Снижается уровень защиты; увеличивается риск компрометации |

## Примеры

### Авторизация

Identity Provider недоступен.

**Варианты:**
- разрешить вход → **Fail Open**
- отказать во входе → **Fail Secure**

В большинстве случаев предпочтителен Fail Secure.

### Проверка прав

```javascript
if (checkPermission(user)) {
    deleteDocument();
}
```

Ошибка проверки прав.

**Плохо (Fail Open):**
```javascript
catch(Exception e) {
    return true;  // ОПАСНО: ошибка → доступ разрешён
}
```

**Хорошо (Fail Secure):**
```javascript
catch(Exception e) {
    return false; // Безопасно: ошибка → доступ запрещён
}
```

### WAF

Если WAF перестал работать:

| Режим | Последствия |
|-------|-------------|
| **Fail Closed** | Сервис недоступен; безопасность сохраняется |
| **Fail Open** | Сервис продолжает работу; защита временно отсутствует |

Выбор зависит от оценки рисков.

## Архитектурное мышление

Fail Secure — это не правило "всегда запрещать".

**Правильный вопрос звучит так:**
> Какое решение безопаснее для данного актива с учётом бизнес-рисков?

Выбор между Fail Secure и Fail Open — это архитектурный компромисс между:
- **Confidentiality**
- **Integrity**
- **Availability**

---

## Security Architect Perspective

> На практике Fail Secure почти никогда не выбирают абсолютно для всех компонентов системы. Архитектору приходится разделять сервисы на критичные (auth, payments, авторизация) — где Fail Secure обязателен, и вспомогательные (рекомендации, логи, аналитика) — где допустим Fail Open. Универсального ответа нет, потому что цена отказа разная: ошибка при проверке прав на финансовую транзакцию и ошибка при загрузке аватарки — это разные уровни риска. Хороший архитектор всегда спрашивает: «Что именно мы защищаем и сколько стоит downtime?»

---

## Связь с другими принципами

- **Least Privilege** — при ошибке пользователь не должен получать дополнительные привилегии
- **Defense in Depth** — отказ одного механизма не должен автоматически приводить к обходу всех остальных
- **Risk Assessment** — выбор режима работы всегда зависит от допустимого уровня риска

## Common Interview Mistakes

### ❌ Категоричный ответ
> «Всегда нужно использовать Fail Secure. Это единственный безопасный подход.»

**Почему это проблема:** Игнорирует real-world constraints. Если каждый сервис работает в Fail Secure, система может стать недоступной при минорном сбое второго-третьего эшелона. Например, если сервис рекомендаций недоступен — это не повод блокировать весь checkout.

**Зрелая формулировка:**
> «Fail Secure должен применяться к компонентам, отвечающим за безопасность (auth, authorization, encryption). Для некритичных сервисов может быть оправдан Fail Open. Выбор всегда основан на анализе: что мы защищаем и какова цена ложного отказа.»

### ❌ Категоричный ответ
> «WAF всегда должен работать в Fail Closed, иначе нет смысла его ставить.»

**Почему это проблема:** WAF в режиме Fail Closed может привести к полной недоступности сайта при любой проблеме с WAF-инфраструктурой. Для e-commerce это может стоить миллионов.

**Зрелая формулировка:**
> «WAF может работать в обоих режимах. Fail Closed — если сайт не может работать без WAF (например, PCI DSS compliance). Fail Open — если downtime стоит дороже, чем временное отсутствие защиты. Компромисс: использовать WAF в активном режиме, но с мониторингом и быстрым переключением.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Почему Fail Secure может конфликтовать с Availability?** | Fail Secure жертвует доступностью ради безопасности. Это часть CIA triad trade-off. |
| **Почему WAF не всегда работает в режиме Fail Closed?** | Потому что downtime может быть дороже, чем временная потеря защиты. Выбор зависит от бизнес-рисков. |
| **В каких случаях Fail Open является осознанным решением?** | Когда цена downtime превышает цену потенциального инцидента (например, рекомендательные сервисы, аналитика). |
| **Что произойдёт при ошибке проверки прав?** | При Fail Secure — отказ в доступе (return false). При Fail Open — небезопасное разрешение доступа (return true). |
| **Чем Fail Secure отличается от Fail Safe?** | Fail Secure защищает данные/активы (замок остаётся закрыт). Fail Safe защищает людей (замок открывается для эвакуации). |

---

## Fail Secure vs Fail Safe

Эти термины часто используют как синонимы, но в инженерной практике их нередко различают.

| | Fail Secure | Fail Safe |
|---|---|---|
| **Главная цель** | Защитить активы и данные | Защитить людей |
| **Пример** | Электронный замок остаётся закрытым при отключении питания | Во время пожара замок автоматически открывается для эвакуации |

---

## Lessons Learned

- Fail Secure — это не абсолютное правило, а принцип принятия решений
- Безопасность всегда оценивается в контексте конкретного актива и бизнес-требований
- Выбор между Fail Secure и Fail Open основан на анализе рисков, а не на универсальных рекомендациях
- Разделяй сервисы на критичные (Fail Secure) и некритичные (Fail Open допустим)
- Не путай Fail Secure (защита данных) и Fail Safe (защита людей)
