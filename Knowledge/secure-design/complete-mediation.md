# Secure Design Principle — Complete Mediation

> **Формат:** Interview-ready. Открыл за 5 минут до собеседования — восстановил тему.

---

## Определение

**Complete Mediation (Полное посредничество)** — принцип Secure Design, согласно которому **каждая** операция доступа должна проверяться независимо, даже если пользователь уже прошёл аутентификацию.

**Основная идея:**
Каждый запрос должен быть проверен. Нельзя доверять предыдущим проверкам.

---

## Зачем нужен Complete Mediation?

Аутентификация отвечает на вопрос: **«Кто ты?»**

Но она не отвечает:
- Можно ли выполнить **именно эту** операцию?
- Можно ли выполнить её **сейчас**?
- Можно ли выполнить её **над этим** объектом?

**Каждый запрос требует отдельной проверки** авторизации и бизнес-правил.

**Главная идея:**
> Перед обработкой запроса стоит спросить: «Мы проверяем доступ **сейчас** или доверяем **предыдущей** проверке?»
>
> Если используется только предыдущая проверка — принцип нарушен.

---

## Complete Mediation vs Check-Once

| | Complete Mediation | Check-Once |
|---|---|---|
| **Когда проверяется** | Каждый запрос | Только при входе или первом обращении |
| **Риск** | Низкий | Высокий (TOCTOU) |
| **Производительность** | Может быть ниже (больше проверок) | Выше |
| **Пример** | Каждый API request проверяет JWT + роль + ownership | Проверили права при логине и закэшировали |

## Примеры

### API

**Плохо (нарушение):**
```javascript
// Проверили права при логине — и всё
app.post('/login', (req, res) => {
    const user = authenticate(req.body);
    req.session.isAdmin = user.role === 'admin';
});

// Дальше используем только флаг
app.delete('/api/orders/:id', (req, res) => {
    if (!req.session.isAdmin) {
        return res.status(403).send('Forbidden');
    }
    // Уязвимость: роль могла быть изменена, пользователь мог быть деактивирован
    Order.delete(req.params.id);
});
```

**Хорошо (Complete Mediation):**
```javascript
// Каждый запрос проверяет всё независимо
app.delete('/api/orders/:id', (req, res) => {
    const user = getCurrentUser(req); // из JWT/session
    
    // Проверка 1: аутентификация
    if (!user) return res.status(401).send('Unauthorized');
    
    // Проверка 2: роль
    if (!user.hasPermission('order:delete')) {
        return res.status(403).send('Forbidden');
    }
    
    // Проверка 3: ownership
    const order = Order.findById(req.params.id);
    if (!order) return res.status(404).send('Not found');
    
    // Проверка 4: бизнес-правила
    if (order.status !== 'pending') {
        return res.status(400).send('Cannot delete shipped order');
    }
    
    // Проверка 5: tenant isolation (для SaaS)
    if (order.tenantId !== user.tenantId) {
        return res.status(403).send('Forbidden');
    }
    
    Order.delete(req.params.id);
});
```

### Интернет-магазин

Удаление заказа — каждый раз проверяется:
- ✅ пользователь — владелец заказа
- ✅ заказ ещё не отправлен
- ✅ пользователь аутентифицирован
- ✅ операция разрешена политикой

### Kubernetes

Каждый API-запрос проходит через:
- **RBAC** — проверка прав
- **Admission Controller** — проверка политик
- **Audit** — логирование

Независимо от предыдущих действий пользователя.

## Архитектурное мышление

Complete Mediation — это баланс между безопасностью и производительностью.

**Правильный вопрос:**
> «Что может измениться между предыдущей проверкой и текущим запросом?»

**Trade-offs:**
- **Безопасность vs Производительность** — кэширование результатов проверки ускоряет, но создаёт TOCTOU
- **Consistency vs Availability** — если сервис авторизации недоступен, что делать?
- **Granularity vs Complexity** — чем детальнее проверки, тем сложнее код

---

## Security Architect Perspective

> Complete Mediation — один из самых часто нарушаемых принципов, особенно в микросервисной архитектуре. Типичная ошибка: сервис A проверил права пользователя и передал результат сервису B (например, в JWT или заголовке), а сервис B доверился этой проверке и не перепроверил. В распределённой системе каждый сервис должен самостоятельно проверять права, потому что контекст мог измениться: пользователя могли деактивировать, права отозвать, а JWT — ещё не истек. Единственное исключение — Policy Enforcement Point (PEP), который централизованно проверяет все запросы, но даже он должен проверять каждый запрос независимо.

---

## TOCTOU (Time-of-Check to Time-of-Use)

Классическая проблема, связанная с нарушением Complete Mediation:

```
1. Система проверяет: есть ли у пользователя доступ? ✅
2. Между проверкой и операцией проходит время
3. Система выполняет операцию

⚠️ За это время доступ мог измениться
```

**Пример:**
```python
# TOCTOU: проверка и операция не атомарны
if user.has_permission('delete'):
    # Между этими строками права могли отозвать
    document.delete()
```

**Решение:** атомарная проверка + выполнение:
```python
# Атомарная операция: проверка и выполнение вместе
db.transaction(
    check_permission(user, document, 'delete'),
    delete_document(document)
)
```

---

## Связь с другими принципами

- **Least Privilege** — определяет, какие права проверять
- **Separation of Privilege** — может требовать нескольких независимых проверок
- **Fail Secure** — при невозможности проверить — запретить (return false, а не true)
- **Defense in Depth** — каждый слой выполняет свои проверки

## Common Interview Mistakes

### ❌ Категоричный ответ
> «Если пользователь аутентифицирован и у него есть JWT/сессия, то авторизация не нужна на каждом endpoint'е — достаточно проверить при входе.»

**Почему это проблема:** Аутентификация и авторизация — разные вещи. JWT подтверждает identity, но не гарантирует, что пользователь имеет право на эту конкретную операцию. Права могли измениться, пользователя могли деактивировать, контекст мог поменяться.

**Зрелая формулировка:**
> «Аутентификация отвечает на вопрос "Кто ты?", авторизация — "Можно ли тебе это?". JWT/сессия решают первую задачу, но не вторую. Каждый endpoint должен сам проверять авторизацию. Даже если это кажется избыточным — это единственный способ избежать TOCTOU и случайного доверия устаревшим данным.»

### ❌ Категоричный ответ
> «Можно закэшировать результат проверки прав — это ускорит систему.»

**Почему это проблема:** Кэш может быть устаревшим. Если права пользователя отозвали, а кэш ещё не обновился — система продолжит разрешать доступ.

**Зрелая формулировка:**
> «Кэширование проверок возможно, но с очень коротким TTL (секунды) и только для read-операций. Для write-операций и чувствительных данных каждая проверка должна быть реальной. Лучшая практика: использовать Policy Engine (OPA/Cedar), который кэширует политики (не результаты проверок) — они меняются редко, а решения всегда свежие.»

### ❌ Категоричный ответ
> «Достаточно проверять права на фронтенде — скрыть кнопку/ссылку.»

**Почему это проблема:** Фронтенд полностью контролируется пользователем. Любой может отправить запрос через DevTools, curl, Postman, Burp Suite. Скрытая кнопка — не защита, а UI/UX решение.

**Зрелая формулировка:**
> «Проверка на фронтенде — это User Experience, а не Security. Она помогает пользователю не видеть то, что ему недоступно, но не защищает от злоумышленника. Backend должен самостоятельно проверять каждый запрос. Фронтенд — это просто ещё один клиент, которому нельзя доверять.»

## Interview Questions

| Вопрос | Ответ |
|--------|-------|
| **Почему недостаточно проверить права только при входе?** | Потому что между входом и операцией права могли измениться (TOCTOU). Каждый запрос требует независимой проверки. |
| **Чем Authentication отличается от Authorization?** | Authentication — «Кто ты?». Authorization — «Что тебе можно?». JWT решает первую задачу, но не вторую. |
| **Почему проверка только на фронтенде опасна?** | Фронтенд полностью под контролем пользователя. Он может отправить любой запрос через DevTools, curl или Burp Suite. |
| **Что такое TOCTOU и как он связан с Complete Mediation?** | Time-of-Check to Time-of-Use — между проверкой и операцией может пройти время, за которое контекст изменится. Complete Mediation требует проверять в момент операции. |
| **Как обеспечить Complete Mediation в микросервисах?** | Каждый сервис должен самостоятельно проверять права, не доверяя проверкам других сервисов. Использовать Policy Engine (OPA) для централизованных, но независимых проверок. |

## Типичные нарушения

| Нарушение | Почему это проблема |
|-----------|-------------------|
| Проверка авторизации только после логина | Между входом и операцией права могли измениться |
| Кэширование результатов проверки доступа | TOCTOU: кэш устарел, доступ уже должен быть закрыт |
| Проверка доступа только в UI | Фронтенд — не защита, все запросы можно подделать |
| Доверие JWT без проверки бизнес-контекста | JWT говорит "кто", но не "можно ли сейчас и над этим объектом" |
| Сервис A проверил → Сервис B доверился | В распределённой системе каждый сервис должен проверять сам |

---

## Lessons Learned

- Аутентификация **не заменяет** авторизацию
- Каждая операция требует **собственной** независимой проверки
- Нельзя доверять предыдущим решениям без повторной валидации (TOCTOU)
- Фронтенд-проверка — это UX, а не Security
- В микросервисах каждый сервис должен проверять права сам
- Policy Engine (OPA/Cedar) помогает централизовать политики, но не отменяет необходимость проверки каждого запроса
